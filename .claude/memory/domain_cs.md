## What's Built

**AI Advisor (Opus-based):** reads the full conversation and calls tools as needed. Handles exchanges, sizing, shipping, product questions, positive feedback, and a `junk` message type (phishing/scam/mass mail, closed at intake with an audit note via [junkDisposition.js](../../customer-service/lib/junkDisposition.js)). Structured output: the legacy `<structured>`-block-in-text shape is the production default; schema-enforced JSON (`advisorOutputSchema.js`) is opt-in via `ADVISOR_SCHEMA_OUTPUT=1`. The parser is mode-aware and handles both. All business rules live in the system prompt. Recent related exchange/refund/defect tickets are injected via `history_summary` for follow-up context. Resilience: malformed output routes to a human placeholder; a 529 on a schema-enforced request falls back to legacy output mode for that draft.

**Closeness-to-Final Judge:** Opus judges every sent draft against what Jamie actually sent (identical / cosmetic / substantive / factual_correction / action_divergence, plus a draft_may_be_right flag). Runs in the daily sync; the digest headline is the substantive-divergence rate. Verdicts in `cs_draft_judgments`; factual-correction verdicts propose a `candidate_fact` or name a `tool_gap`.

**Auto-send (shadow):** gate (`autosendGate.js`) with a hardcoded never-list (money/orders/actions never eligible) plus a per-category `system_flags` allowlist only Jamie promotes. Shadow mode marks would-have-sent drafts (`auto_close_path='autosend_shadow'`); nothing sends. Dashboard allowlist panel, Closed-tab AUTO filter, digest dry-run line with judge-verified would-have-erred count.

**Steer & Send (shadow):** measures whether a steered regen could skip the final review glance. Gate (`steerSendGate.js`): deterministic checks (autosend never-list, any/changed `action_type` is ineligible, prose-only scope) then an Opus correctness verifier that fails closed. Every dashboard steered regen records a `would_send` verdict to `steer_send_shadow`; nothing sends.

**Training-signal capture:** all three send paths log to `cs_ai_feedback_log` (sent/edited, `bypassed_*`, `manual_*`) plus `operator_steer` and `regen_count`.

**Tool Ecosystem (30+ MCP tools):** lookup (customer, orders, products), actions (create/edit/refund orders, exchanges, invoice orders, wholesale orders, consolidate/split, warehouse holds, address and email changes via `update_customer`, discount codes, colourway registration, away mode), analytics (LTV, margins, inventory, allocation, delivery estimates, reviews), knowledge (CS history search, FAQ, sizing guide, `search_knowledge`, `compare_products`). All agentic loops (advisor main+shadow, operator main+shadow, ad hoc) run on one engine, `customer-service/lib/runToolLoop.js`.

**Dashboard (web-based, ops.rubyshines.com on Railway):** real-time Gorgias ticket queue with tabs (New, Follow-up, Parked, Snoozed, On Me, Bug, Closed) and global ticket search. Operators review AI drafts and approve/edit/steer; one-click Execute & Send runs the staged operator action and sends. Operator agent for complex order manipulations. Ad Hoc Operator tab for context-free queries and actions against all CS tools (Opus, ephemeral history, PDF upload). Facts panel, auto-send allowlist panel, stats page (operator touch time). Mobile-responsive PWA.

**Intake Pipeline:** Gorgias ticket webhooks and Gmail CS parsing, both feeding the advisor, storing drafts in Supabase, and auto-assigning handled tickets to "RUBIES AI" in Gorgias. Intake also auto-executes same-country address changes and advisor-proposed warehouse holds (best-effort), with a backstop hold sweep ([holdReconcile.js](../../customer-service/lib/holdReconcile.js)) on the always-on webhook server. Duplicate/continuation handling in [ticketContinuation.js](../../customer-service/lib/ticketContinuation.js).

**Spam gate:** the Gorgias spam flag never drops a ticket silently. Gorgias sends no message webhook for customer messages on spam-flagged tickets, so the gate ([spamGate.js](../../customer-service/sync/lib/spamGate.js)) is the only path in for that population: known customers ([knownCustomer.js](../../customer-service/lib/knownCustomer.js)) and triage-verdict persons are drafted via normal intake, pitches and junk are closed with an audit note, rescues are reported in the digest. Two callers: the nightly reconcile (full population) and the webhook server every 15 min over recently touched tickets.

**Drift reconciler (`customer-service/sync/gorgiasAdvisorResync.js`, daily):** triages status-drift tickets via [driftTriage.js](../../customer-service/lib/driftTriage.js), auto-closes noise, reports real misses, runs the follow-up sweep, the closeness judge, the note lifecycle, and stale pending-draft cleanup.

**Exchange System:** two-phase. Phase 1: AI determines size, creates a Shopify draft order, shows a preview. Phase 2: operator confirms, marks paid. Uses only FULFILLED non-cancelled orders for current size. Differing-item exchanges plan through `exchange_difference` (read-only: applies live discounts per line, credits returns at actual-paid, recommends invoice / auto-refund / free); the advisor reaches the same computation through `exchange_price_check`, which returns a settlement verdict and no figures. See [exchangeMath.js](../../customer-service/lib/exchangeMath.js) and [tools/exchangeDifference.js](../../customer-service/lib/tools/exchangeDifference.js).

**Donation Routing:** after an exchange, routes old items to LGBTQ+ partners by geography (Google Maps geocoding + haversine), load-balanced across the closest partners. Skips for defects.

**Knowledge Base:** source-linked, trust-tagged articles (published site tier + founder-reviewed reply-corpus tier) with Voyage embeddings, searched via `search_knowledge` (kill switch: system_flag `advisor_kb_search`). Weekly refresh re-harvests the site and flags drifted sources (`customer-service/sync/refreshKb.js`). Pipeline and review-sheet tooling in `customer-service/import/`.

**Operator facts:** `advisor_facts` table, active facts injected verbatim into the advisor prompt; the judge proposes candidates; dashboard Facts panel approves/rejects/retires with optional expiry. Logic in [advisorFacts.js](../../customer-service/lib/advisorFacts.js); schema `customer-service/drafter/advisor-facts-schema.sql`.

**Auto Follow-ups:** two stages fired by the daily sweep. A Haiku classifier first closes tickets that already look resolved. Stage 1: care@ via Gorgias, re-snooze. Stage 2: personal jamie@ via SendGrid, internal note in Gorgias, close. A customer reply during snooze resets the stage. Logic in `customer-service/lib/followUp.js`.

**Outbound outreach:** `create_outreach_ticket` composes a single reviewed draft (Gorgias ticket created lazily on send); `sendIncidentOutreach` in [customerOutreach.js](../../customer-service/lib/customerOutreach.js) handles batch incident sends. Outbound drafts carry `structured_output.outreach_kind` so Refresh re-runs the generator that produced them; a sent outbound draft is never refreshed back into the queue.

**Unnotified Pre-Order Outreach (auto-drafter):** detects orders waiting on an item the customer was never told about, two ways: a disclosure gap (paid item at zero stock with no `Pre-order` line attribute, e.g. Shop App orders) and a de-allocation (the warehouse hands back a reserved unit, detected as a transition against stored prior state in `order_line_allocation_state`, written hourly by [deallocationWatch.js](../../reports/lib/deallocationWatch.js)). Each candidate is classified A/B/C, verified against live Warehance, gets a done-for-you swap staged where an identical-fit size is in stock, and seeds a pending advisor draft. Runs as a sweep on the always-on webhook server. See [reports/lib/unnotifiedPreOrder.js](../../reports/lib/unnotifiedPreOrder.js); per-order allocation is reconstructed in [orderAllocation.js](../../reports/lib/orderAllocation.js).

**Pre-order lifecycle tools:** `preorder_hygiene` reconciles open unfulfilled orders against live Shopify + Warehance and lists the waiting population by promised text; `preorder_update_notice` sends a delay wave (two variants, optional refund offer, plain care@ email via SendGrid, live sends logged to `preorder_notifications` for dedupe; dry_run, test_send, send). CLIs `scripts/preorderHygiene.js`, `scripts/preorderUpdateNotice.js`; logic in [preOrderLifecycle.js](../../customer-service/lib/merchandising/preOrderLifecycle.js).

**Downstream draft guards (deterministic, visibility-only ⚠️ banners via `prescription.flags`):** reply containment ([replyContainment.js](../../customer-service/lib/replyContainment.js)), bot-flow selection coverage ([selectionCoverage.js](../../customer-service/lib/selectionCoverage.js)), duplicate-goods warning on `create_invoice_order`, auto-action fallbacks.

**Away mode:** first-contact out-of-office ack gated on the `cs_away_mode` system flag with `expires_at`; controllable via the `away_mode` MCP tool from the mobile console.

**Eval tooling:** pinned scenario suite in `customer-service/test/scenarios/`; `scripts/repeatScenarios.js` (repeat runs, FLAKY detection); `scripts/modelSwapEval.js` (candidate vs incumbent control arm); shadow eval via `cs_diagnostics`.

## Key Decisions

- **Agentic loops, not decision trees.** Opus controls flow; all exchange/sizing/response rules live in the advisor prompt, not in code. The old deterministic sizing tree was deleted; `sizingEngine.js` owns only sizing utilities (nicknames, classification, size lists and adjacency, grading deltas, chart category, one-piece fit), nothing that decides what to say.
- **One shared tool-loop engine.** Every agentic loop runs on `runToolLoop.js`; callers inject divergent behaviour via callbacks. New agents use it rather than hand-rolling the loop.
- **Structured output:** the advisor returns `_structured` JSON alongside customer-facing markdown; the dashboard consumes the structured data directly.
- **Advisor guidance that lives only in the JSON schema has never shipped.** Field semantics exist in two copies (schema descriptions and the legacy template) and production sends the template, so a rule that reads as ignored may never have been sent. Parity is test-enforced and the operator-action-summary spec is single-sourced.
- **Tool calls precede customer-facing prose.** The advisor saves only the last round's text, so the customer email must be written entirely in the final round after all tool results. Same rule for the operator agent.
- **Exchange sizing from SKU, not variant title:** the last SKU segment is the canonical size.
- **A product's size range has one source: the catalog.** `getSizeList` reads the `kid_sizes` / `adult_sizes` Shopify metafields loaded with the product cache; youth and adult runs are stored separately; a product with no run in one group returns null rather than a generic fallback; accessories have no size axis. `product_cs_config.sizes_override` is retired because a hand-maintained range beside the catalog always drifts.
- **The `sizingEngine` test fixture is generated from live data, never hand-written.** Every hand-edited version drifted from production and either hid a bug or asserted a false fact about a real product.
- **Knowledge precedence: live data tools > operator facts > KB search > never guess.** Authoritative live facts stay in tables behind tools; `advisor_facts` are injected verbatim; the KB is searched for durable facts and complements live tools. Look-up-able facts (measurements, prices, partner addresses) are never KB prose. Discretion-gated facts carry FOUNDER DISCRETION markers; the advisor routes, never offers.
- **Operator facts are injected, not retrieved.** The failure being fixed is the advisor not knowing a fact exists, so retrieval (which requires knowing to look) cannot fix it. Growth valves: Jamie's approval gate, expiry on perishable facts, dedupe-on-propose, retrieval fallback only if the set grows very large. Facts state durable truths; live data wins on conflict.
- **A fact earns its place only when no system of record could hold it.** The facts list drifted into a general knowledge base because the judge minted one fact per correction; an audit retired most of them. Look-up-able facts live in their systems of record; when the judge declines a fact for that reason it names the tool that should have answered (`cs_draft_judgments.tool_gap`), listed in the digest as the tool backlog. What remains is founder knowledge with nowhere else to live.
- **A wrong operator fact cannot be fixed with a prompt rule.** Facts outrank KB search, so an advisor holding a bad fact answers confidently and never searches. Sweep three layers: correct the fact, re-extract the KB candidate (the weekly refresh only flags drift, never re-extracts), and fix the site copy. Facts must be symmetric across products the advisor will compare, or the model invents the missing contrast.
- **Product-cut comparisons live on `product_cs_config.style_switch`, surfaced by `compare_products`.** PDP blurbs are not comparable, so the model guessed. A half-filled comparison set is worse than empty, so every higher-leg style is marked. Deliberately not built: a measured comparison from `tech_pack_specs`; specs verify claims during audits and are never quoted to customers at runtime.
- **`style_switch` carries two meanings that must not be collapsed:** `isTarget` is the cut fact, `recommendFor` is the suggestion (scoped by tight legs, age groups, everyday). A style can be a wider cut without being what we suggest. Founder wording ruling: name the all-day pick, never state a comfort trade-off outright, and for tight legs with a fitting waist lead with the roomier opening and give "cut higher" as the reason (the phrasing is a verbatim prompt template because positive templates stick and descriptions drift).
- **Supply has three states and the middle one carries its own name:** in stock now / arriving soon enough to be worth waiting for / not available. An arriving style sits beside in-stock ones with `availability` and `back_in_stock`, with a verbatim prompt template and an explicit list of internal fields that never reach a customer. Founder ruling: fit leads, an arriving style is not demoted for arriving; stock only breaks ties. Framed as an exchange we hold, never a purchase.
- **`inbound_shipments` is the restock authority; the `pre_order_date` metafield answers a different question.** The metafield is the promise shown at checkout for an item already on the order; the inbound row decides whether a style is recommendable and which date we quote. No inbound row means not recommendable. An arrived shipment is judged on its sellable date, not its ETA.
- **Every entity in a tool payload must answer the same question, or the model reads the answer across.** When the advisor compares products, a field present on one and absent on its sibling is used for both. Colour availability comes from one shared helper for source and alternatives; `colorsInStock` and `colorsOutOfStock` partition the colours (asserted by test) and both carry `arriving_colors`, because "which colours can ship" and "is the one they asked for coming back" are two questions and answering only the first ends the conversation. `restockEta`'s offer window decides whether a wait is worth offering; a colour past it is absent rather than hedged.
- **A colourway goes live in stages, and only the variants are self-evident.** `register_colourway` ([tools/colourway.js](../../customer-service/lib/tools/colourway.js)) writes exactly one thing, the colour metafields recomputed from existing variants, and reports everything else (stale facts, KB) because retiring a fact is Jamie's call. The metafield is availability-blind; what can ship is `colorsInStock`'s question.
- **A customer-facing product name comes from the curated nickname, never the handle.** A handle is an SEO slug and routinely disagrees with the name. `renderVariantForCustomer` reads `product_cs_config.nickname` (same column as `getProductNickname`) and falls back to the product title, since a wrong name is indistinguishable from a real one while a verbose one only reads as clumsy.
- **Advisor prompt changes:** trace the execution path, read audit trails, and check existing rules before modifying; don't add rules that duplicate existing logic. Always check stored ticket data in Supabase before diagnosing advisor issues.
- **Diagnosing a flagged draft: find the cause before reaching for a lever.** Four causes, four fixes: (a) the advisor didn't know something only Jamie knows, propose an `advisor_facts` entry, not a rule (the largest cluster); (b) the prompt told it the wrong thing, fix or delete that rule; (c) the prompt told it the right thing and it did not comply, grep the prompt first and remove competing instructions rather than adding another rule; (d) a tone sample contradicts a rule, fix the sample. Read `draft_history[0]`, never `draft_response`, because on a steered ticket the stored draft is the model obeying Jamie's correction. One draft is a hypothesis; measure the pattern against the unfiltered population before changing anything, since a rate computed only on steered or edited drafts is biased by construction.
- **Advisor quality metrics count only drafts the advisor wrote, and an unedited send is not approval.** `cs_ai_drafts` also holds follow-up templates, operator-composed replies and simulator traffic, so any metric must filter to `source='poller'` + `draft_kind='advisor_draft'`. Jamie often ships drafts he would not have written rather than rewrite them, so an unedited send is an unlabeled sample, not a positive one.
- **Accuracy-eval ground truth is Jamie's sent reply.** Compare `draft_response` to `sent_response`; for actions, ground truth is what the sent prose says was done, not `actions[]`. Verify factual claims against DB/catalog, not the draft.
- **Validate advisor prompt/tool changes with order-independent scenario tests, not live regen.** Re-running historical tickets is confounded by order-state drift. Add a pinned scenario for every validated fix. Testing workflow: pull real conversations from Supabase, run via node, not MCP.
- **A pinned scenario whose anchor has shipped SKIPS rather than fails, and a zero exit is not evidence it ran.** Assertions key on behaviour, not the anchor's product; `repeatScenarios.js` flags any scenario that produced no assertions. When a behaviour only fires under a transient state of the world, stub the inputs and assert the stubs were exercised.
- **Advisor scenario results are non-deterministic; a single run proves nothing.** Temperature is not settable, so any accuracy claim needs `--repeat 3` minimum and a mixed result reports FLAKY. Do not fix flakiness by loosening assertions without reading the drafts; most flaky scenarios were catching real defects.
- **Model swaps are qualified by scenario-suite-plus-control, not shadow eval.** `modelSwapEval.js` re-runs every candidate failure against the incumbent so pre-existing failures and drift are not misattributed. The model override is an eval-only preload, deliberately not an env var, so no production runtime can be flipped by a stray variable. Shadow eval remains for long-horizon A/B on a downgrade candidate.
- **Accuracy-sweep cadence is change-driven, surfaced at orient.** Method: zero-API eval (Supabase reads + subagents judging draft vs sent), never live regen. Recommend a new sweep when roughly 8+ commits have touched the advisor, or 150+ new sent drafts have accumulated under a stable prompt, or the substantive-edit rate rises above baseline.
- **Response register: "one move per message" plus explanation gating.** Numeric word-count targets were removed because they caused budget-filling. Per issue pick one move (act, ask, or explain) plus only its required attachments. Explanations fire only on triggers: the shaping-expectations template only when the customer questions the shaping itself (three fit states: a stated loose/tight direction gets a sizing move; no fit info or fit-stated-as-fine gets the template, never a product pitch before measurements); validate + causal explanation only for RUBIES-caused failures; plain fit complaints get a size suggestion or one measurement question. Exchange confirmations end at the ship day. A blanket apology-flag banner was tried and removed as noise; if sorry-drift recurs the answer is a smarter gate.
- **Tone samples and verbatim templates outrank rules.** A positive template (in `cs_tone_samples` or the prompt itself) beats a negative rule stated elsewhere, so whenever a voice ruling changes, sweep both the samples and the prompt templates for contradictions rather than adding louder rules. Founder idioms that look like apologies are kept verbatim and fenced via the sample's `context` field.
- **An instruction inside a tool result outranks any prompt rule, so state-dependent copy is decided by the tool.** The last thing the model reads before composing wins, and tool results are last. Donation routing copy is used as-is from the tool's `response_text`; the already-given-address state is a branch in the routing tool returning a one-line confirmation, triggered off the sent text (what the customer actually holds), not routing metadata. Suppressing the re-route matters because routing is weighted-random and a second call could split one return across two partners.
- **Reasoning leakage is contained by a model-read anchor slice, not another prefix strip.** Deterministic strips cannot catch leaks with no fixed position. A small model returns verbatim anchors, never prose ([replyContainment.js](../../customer-service/lib/replyContainment.js)), so the reply is always a contiguous substring of what the advisor wrote; every failure path keeps the original and raises the banner. A front cut must leave something that opens like a greeting. Haiku was chosen by measurement over Sonnet; re-run `scripts/evalReplyContainment.js` before changing it. At this incidence a prompt rule cannot be told from noise, which is the standing case for accepting variance and adding a downstream guard.
- **A bot-flow item selection is the scope of the action, enforced in the prompt and again downstream.** The advisor occasionally relabels an itemized list as a product family and stages an action one line short; incidence sits below what the scenario suite can resolve, so the guard is a deterministic banner ([selectionCoverage.js](../../customer-service/lib/selectionCoverage.js)). Visibility-only because a deliberately narrower action is legitimate; whole-order action types are exempt by type. Calibrate with `scripts/replaySelectionGuard.js` against the population, never one ticket.
- **Corpus-harvest learnings:** founder statements age, so every mined fact carries its date and newer supersedes older; founder review is the scarce resource, so tool-verified triage auto-accepts what it can and only judgment calls reach the review sheet; edit-based loops can't see what the founder tolerates but wouldn't write, so his from-scratch replies are the voice ground truth.
- **Founder review sheets: one Google Sheet, checkbox loop.** Batches for Jamie to approve are published as a tab in the shared review spreadsheet via [publishReviewSheets.js](../../customer-service/import/publishReviewSheets.js), read back with `--read`, applied with `--read --apply`. Markdown files are not a review medium.
- **Gorgias writes before Supabase writes.** Call Gorgias first and let errors propagate; only update `cs_tickets` after Gorgias confirms. Never wrap the Gorgias call in try/catch, which causes silent split-brain.
- **Gmail intake claims its row atomically.** Pub/Sub is at-least-once, so `processMessage` conditionally marks `processed_at` as its first action; secondary defence checks Gorgias for existing open tickets by email.
- **Duplicate auto-close: first contact only, and continuations are transplanted, never closed away.** Duplicate detection returns null once a ticket has a second customer message. A first-contact ticket that advances an existing conversation (a reply that failed to thread) is a continuation: the message moves onto the surviving ticket as a real customer message, the stray closes with pointer notes, and the survivor's follow-up cycle resets. Transplant before reopening the survivor or the snooze-expiry path fires a nudge.
- **The operator's message view must show at least what the advisor read.** Gorgias's `stripped_html` (rendered) and plain text (read by the advisor) disagree, and the HTML often loses lines. One shared renderer ([messageBody.js](../../customer-service/dashboard/public/messageBody.js)) serves every render path, falls back to plain text when the HTML is missing substantive content, and tests fail if a new path skips it. Losing formatting is always cheaper than hiding words the advisor acted on.
- **Drift sync auto-resolves noise, reports real misses, never backfills drafts.** Duplicates, emoji-reaction reopens and vendor spam are auto-closed with an audit note; genuine customer misses surface in the digest but are not auto-drafted, so intake bugs stay visible (`--execute` is the manual drafting path). Bounce detection runs before triage, because a delivery failure reopens a ticket and would otherwise read as a real miss. Spam-flagged misses are the exception and are drafted by the gate, since for them the sweep is the designed path.
- **The spam triage classifier is population-aware.** On drift tickets uncertain resolves to CUSTOMER; on spam-flagged tickets the Gorgias flag counts as evidence and uncertain resolves to JUNK, because the CUSTOMER tie-break drafted phishing into the queue. Deterministic guards fail toward the queue: a known customer or a thread an agent replied on is never auto-closed. Accepted trade-off: a flagged bare footer-style question from an unknown sender closes unanswered with an audit note.
- **Auto follow-ups run from the daily sweep; dedup by `follow_up_stage`.** Gorgias sends no event on snooze expiry, so the sweep is the engine. Stage advances atomically on `cs_tickets.follow_up_stage`; customer replies reset it. Stage 1 is sent as the AI bot so intake skips it; Stage 2 closes the ticket. Follow-up sends refresh the conversation snapshot and Stage 2 leaves an internal note so the dashboard reflects it.
- **`message_type` taxonomies are separate.** `cs_tickets.message_type` is the canonical inquiry category ([messageTypes.js](../../customer-service/lib/messageTypes.js)); `intake_state.message_type` inside structured output is a sub-taxonomy for item-level decisions. Non-canonical values coerce to `uncategorized`.
- **`pending_operator` / On Me is the state where Jamie owes the response.** Snoozes Gorgias without sending and suppresses auto follow-up; a customer reply returns the ticket to open. In the daily report On Me takes precedence over Waiting on Response.
- **Bug is a flag, not a status.** "Blocked on an advisor fix" outlives the conversation state it was found in, so `bug_flagged_at` / `bug_note` live on `cs_tickets` and the Bug tab spans every status without touching the status machine.
- **Outbound-initiated tickets are modeled as snoozed-after-reply** (`status='snoozed'`, `initiated_by='operator'`, seeded draft with `source='operator_outreach'`), so normal snooze-expiry follow-up plumbing applies with no extra state.
- **Single-draft outreach stages with a NULL `gorgias_ticket_id`; Gorgias is created lazily on send.** Use `create_outreach_ticket` for bespoke drafts needing review before any external write; use `sendIncidentOutreach` for batches. Outreach drafts can carry a paired operator action. The null id is a state every draft button handler must hold; guard at the point that reads the id, and test each button on the null path.
- **Per-incident outreach: durable substrate + one-off driver.** A per-incident driver in `scripts/_<incident>-outreach.js` hands the order list to `sendIncidentOutreach()`; modes are flags (print-only, `--test-send`, `--send`). The driver is disposable, the infrastructure permanent.
- **Refresh on a templated outreach re-runs its own generator; a sent outbound draft is a record, not a draft.** An unsteered Refresh asks "does this still hold?", so detection re-runs and a no-longer-valid outreach has its body replaced with the reason plus a flag rather than left looking sendable; a steer hands off to the general composer. Refresh on a sent outbound draft is refused, because unlike the inbound path there is no customer reply making a reset safe.
- **Completed operator actions are filed inline in the ticket timeline; every consumer reads the ticket-level union.** Actions append to `cs_ai_drafts.actions[]`; because each customer reply creates a fresh draft row, the timeline, the operator agent and the advisor's context all union across all the ticket's drafts (`unionTicketActions` in [draftActions.js](../../customer-service/lib/draftActions.js)). The log records attempts, not guaranteed successes, so consumers read each line's outcome marker. `action_result` is the in-flight scratchpad, cleared on completion and terminal draft events; confirm buttons key off the server-computed `chat_pending_preview` flag, never client regex.
- **`action_type` taxonomy is operator-write verbs, mostly 1:1 with tools.** Adding one requires a matching MCP tool, the `parseStructured` whitelist in `aiAdvisor.js`, and the dashboard prefill.
- **Operator agent confirmation handling: tool call mandatory, never re-preview.** On any confirm signal the next action is the same tool with `confirmed: true`; a confirmation scopes to the most recent still-pending preview, and executed or cancelled previews never re-fire.
- **Operator agent hard-stops on infrastructure errors.** GraphQL errors, 5xx, stack traces and fetch failures get one reply with the excerpt and no workaround attempts; business-outcome errors (order not found, OOS) are handled normally.
- **One-click Execute & Send runs the operator action then sends, gated on the AUTO_CONFIRM verdict.** Auto-confirms only when the verdict is SAFE and exactly one clean awaiting-confirmation write was previewed; HOLD on divergence, question, error or multi-write. Action before send; a phase-2 failure sends no email. Deterministic guards (e.g. the duplicate-goods marker) are read by the gate directly so a self-graded SAFE cannot auto-send past them.
- **Any change to an UNFULFILLED order freezes it with a warehouse hold before it can ship.** All item modifies and all cancels route to `warehouse_hold` (or `cancellation` with a protective hold); a firm cancel with no stated reason is still ambivalent. `order_modification` is reserved for exactly one case, a same-country address change, because the advisor's `action_type` is what gates the backstop sweep and a mislabelled edit gets neither hold nor backstop. Preserve that scoping statement in any future prompt edit.
- **Advisor-proposed holds execute at intake (best-effort) with a backstop sweep that guarantees the hold lands.** The intake attempt often fails because the order is not yet in Warehance; failures go to the audit trail. `reconcilePendingHolds` places any proposed-but-unexecuted hold once the order appears, gives up loudly when the order is already in fulfillment, and never writes a false `action_executed_at`. Hold target resolves via `holdTargetOrderNumber()`, where the advisor's explicit `action_order_number` wins over the ticket-linked order after a redirect. `handleWarehouseHold` refuses fulfilled/cancelled orders because Warehance otherwise accepts a meaningless hold on shipped orders.
- **Same-country address changes auto-apply at intake; cross-border and unverifiable ones fall back to a protective hold.** The new address is validated by geocode plausibility ([addressValidation.js](../../customer-service/lib/addressValidation.js)) and applied via `edit_order` before the draft is filed so the past-tense reply is true. The address is validated, never rewritten, since normalization can drop unit numbers. Fallbacks raise a `prescription.flags` entry, which renders as the ⚠️ banner on the ticket.
- **All order-creation tools accept a `shipping_address` override, and the recipient name is part of the address.** A shared helper in [orderUtils.js](../../customer-service/lib/orderUtils.js) resolves overrides identically on every path (including `edit_order`) and always writes the complete address. A new `address1` with no `address2` clears `address2`; the recipient name is copied verbatim, typos included (a judgment in the tool description, not a code guard); every ship-to preview renders the name.
- **Default shipping speed is `standard` across all order-creation tools;** the operator must explicitly pass `expedited`.
- **An order edit settles against what the customer PAID, and a SKU never identifies a line.** Bundle orders carry the same variant on two lines at different prices, so line resolution takes a line ID and an ambiguous SKU fails loudly. Shopify re-applies order-level discount codes to lines added in an edit but not manual, bundle or automatic discounts, so a replacement line is priced against the pre-code base and committed totals are verified after commit (the preview cannot see it). `totalPriceSet` grows with edits; `netPaymentSet` is the only figure that says whether the customer is up or down.
- **A swap declared even never moves money.** Fixed-amount discounts are shop-currency and reinterpreted in presentment currency, so even swaps use a percentage. `orderEditCommit`'s `notifyCustomer` defaults to false because Shopify would invoice at commit ahead of our settlement logic. Phase 1 refuses to stage an edit Shopify does not price to zero, and Phase 2 reports any residual for manual settlement rather than invoicing or auto-refunding on arithmetic that just proved wrong.
- **A tool that creates an order carrying free copies of live lines ships them twice.** `create_invoice_order` has no source order, so its free lines are only for goods the customer no longer has; unfulfilled-order changes go through `edit_order`. The rule lives in the tool description (the text nearest the decision wins) and a deterministic guard checks live orders for overlapping SKUs. It warns rather than refuses, because a repeat customer can legitimately hold the same SKU on a live order.
- **`consolidate_orders` merges two unfulfilled orders without cancel/refund; `split_shipment` merge mode prevents double-boxing.** Consolidate adds the dropped order's items to the keeper at full discount, placeholder-fulfills the dropped order and refunds shipping when the threshold is met; two-phase, refuses on partial fulfillment, Warehance in-progress or different customers. Split merge mode placeholder-fulfills in-stock items on the source and cross-notes both orders.
- **A split is only a pre-order when the goods are actually on pre-order.** `split_kind` is required and deliberately not defaulted, since a wrong default is what made a mislabelled in-stock split silent (the `Pre-order` property is the canonical sweep signal and renders on the customer's order page). A `hold` split places the Warehance hold itself and reports NOT PLACED if it fails; merge mode is exempt.
- **Exchange settlement is computed, never judged by the advisor.** The advisor calls `exchange_price_check`, which shares `planExchangeDifference` with the operator agent's tool so reply and execution cannot price a swap differently, and returns a verdict plus the sentence to write with no figures. Policy in `settleExchange`: money owed back always refunds; an upcharge at or under the waive threshold is waived and framed as a favour; above it invoices; adding items with nothing coming back always invoices. A customer's ask to be charged is an input to the calculation, not an exception layered on top, and a failed check fails closed in the tool result.
- **Refund/cancellation confirmations never state an exact dollar amount.** Both the draft and `operator_action_summary` omit the figure; the tool computes it. Exception: `invoice_kept_items` and custom refunds (DDP duties) pass an explicit amount.
- **One replacement order per exchange request, even when returned items came from different original orders.** `original_order_id` only sets the back-link and ship-to. The operator-action-summary template is single-order by shape, so check the template before adding a rule; a positive template outranks a rule stated elsewhere.
- **Wholesale lines set a custom `priceOverride`, never a discount.** Fixed-amount discounts on a foreign-currency draft reconvert at checkout; a custom line price locks at the draft's FX rate and keeps the variant link, so invoice equals checkout. Profitability revenue is computed net of line discounts.
- **CS comp codes append to per-level "Thank You N" bucket discounts, never "Welcome".** One shared discount per percent level keeps the admin list tidy; `usageLimit` applies per code so each stays single-use. Because our discounts are code pools, revocation targets the individual redeem code and only deactivates the node when it owns exactly one code.
- **Pre-order detection reads Shopify line-item `Pre-order` customAttributes, not just product tags.** The attribute persists after the tag is removed.
- **Pre-order wave truth is live Shopify + Warehance, never the mirror.** Mirror line attributes and open/closed state drift, and Warehance `ready_to_ship === false` is the only valid waiting signal since Shopify inventory 0 can be stock reserved on that very order. Run `preorder_hygiene` before every wave.
- **Unnotified pre-order outreach is detection + outreach, not channel blocking, and is triggered by warehouse allocation, not elapsed days.** Unpublishing from the Shop channel hides in-stock variants too. Warehance allocates within minutes when stock exists, so an order still unallocated an hour after purchase is the shortage signal. The drafter is the sole writer of these drafts (the daily report only reads its `author='auto'` notes), idempotent via an unresolved auto note with a staleness guard; the age threshold is shared with the report via `shared/businessDays.js`. De-allocation is a transition and needs a stored prior observation, so it is exempt from the order-age gate; the first observation seeds rather than fires.
- **A per-SKU counter cannot answer a per-order question.** Warehance exposes only SKU totals and an order-level `has_unallocated_products` boolean (confirmed against its OpenAPI spec; there is no per-line allocation to fetch). "Is this item reserved for this order?" is reconstructed in [orderAllocation.js](../../reports/lib/orderAllocation.js) by replaying the oldest-first walk over the open order book against the pool of sellable units (`allocated + available`, never `on_hand`, which includes non-sellable bins), validated against the counters it does not consume. All three former call sites (pre-order drafter, `get_order_allocation`, `fulfillmentChecker`) use it, because inline re-answers drifted into contradiction with no test failing. Only over-counted demand may disqualify a SKU; `has_unallocated_products` outranks the reconstruction; `ready_to_ship === false` is not evidence of a stock problem.
- **An identical-fit swap is not a choice, so stop asking.** An in-stock, same-price, youth/adult-equivalent size is the same garment on the other chart; the swap is staged for every case because it reduces the order to waiting only on what the customer was already told about. The swap-done email's closing must track what the order is still waiting on.
- **Operator notes and order-alert notes.** An unresolved operator note overrides pre-order auto-classification in the daily report. `order_alert_notes.alert_type` records the intake pipeline (`unfulfilled`, `shipping`), never operator states. Notes have an automated lifecycle ([noteLifecycle.js](../../customer-service/lib/noteLifecycle.js)): outreach notes resolve when work demonstrably finishes; operator judgment notes are never auto-resolved and age visibly instead; an order ever auto-drafted is never auto-drafted again. Unresolved notes on fulfilled orders surface in Waiting on Response. `cs_tickets.order_number` appears with and without a leading `#`; match both.
- **An email change is a cross-system operation, and a taken address is a merge, not an error.** `update_customer` is two-phase and owns Shopify (update or mergeable-checked merge), Klaviyo (patch or profile-merge; consent never granted), Gorgias reply re-routing, and the mirror (id-first upsert so a rename never forks the `customers` row). Logic in [emailChange.js](../../customer-service/lib/emailChange.js); merge previews HOLD because a merge is irreversible.
- **Delivered-but-not-received is handled directly.** The advisor states tracking facts, confirms the ship-to address, suggests checking around, offers a reship and sets `needs_info`; it never tells the customer to file a carrier claim on first contact.
- **Standardized email signature + one-time advocacy P.S.** All outbound CS mail signs off from [signatures.js](../../customer-service/lib/signatures.js), test-enforced so any listed sender that hardcodes a sign-off fails. Only on genuine delight the advisor appends a short "spread the word" P.S. (parents vs self-buyers framing); asked once per customer ever, recorded by matching the sent body into `advocacy_asks_sent`. A structured `closing_ask` field was tried and dropped because the model drifted on the field but not the prose.
- **`route_to_human` always carries a routing_reason; refund-pattern flags are visibility-only.** Refunds process normally; the advisor raises ⚠️ refund-pattern flags without changing the reply and routes to Jamie only at 2+ previously refunded orders. Flagged refunds trigger a locked donation proof ask (never advisor-composed, never refund-gating). Both flag patterns require the whole order coming back; a partial return is ordinary. Refund policy deliberately unchanged after assessment.
- **Operator-absence features must switch themselves off, and the control surface must be reachable from where the operator will be.** `system_flags.expires_at` makes an expired flag read as disabled, so away mode's window is the switch. The ack claims idempotency on `cs_tickets.away_ack_sent_at` because the draft row's uniqueness is already held by the advisor draft. Away mode shipped CLI-only and never got used, so it is also an MCP tool usable from the mobile console.
- **Operator touch time is accumulated keyboard/mouse time, not elapsed time.** Idle and tab-hide pause it; localStorage persists it; captured on every terminal action and summed per ticket. Headline metric is total time on CS per day/week.
