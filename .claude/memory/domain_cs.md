## What's Built

**AI Advisor (Opus-based):** AI reads full conversation + calls tools as needed. Handles exchanges, sizing, shipping, product questions, positive feedback. Structured output: the legacy `<structured>`-block-in-text shape is the production default (schema-enforced JSON via `advisorOutputSchema.js` shipped 2026-06-11 but was turned OFF by default 2026-06-13 — grammar requests are 3-20x slower and the first thing Anthropic load-sheds; opt back in with `ADVISOR_SCHEMA_OUTPUT=1`). The output parser is mode-aware and handles both shapes. All business rules live in the system prompt. Injects recent related exchange/refund/defect tickets via history_summary for second-round follow-up context. Resilience layers: malformed-output → route-to-human placeholder; 529 on large schema-enforced requests → automatic one-flip fallback to the legacy `<structured>` output mode per draft.

**Closeness-to-Final Judge (2026-06-10):** continuous quality yardstick — Opus judges every sent draft against what Jamie actually sent (categories: identical/cosmetic/substantive/factual_correction/action_divergence + a draft_may_be_right flag). Runs in the daily sync; digest headline = substantive-divergence rate (supersedes raw edit-rate). Verdicts in `cs_draft_judgments`. 90-day baseline: closing 97% clean, overall divergence improving over time.

**Auto-send (shadow phase, 2026-06-11):** gate (`autosendGate.js`) with a hardcoded never-list (money/orders/actions never eligible) + per-category `system_flags` allowlist that only Jamie promotes. Shadow mode marks would-have-sent drafts (`auto_close_path='autosend_shadow'`) — nothing sends. Dashboard: Auto-send allowlist panel + Closed-tab AUTO filter; digest dry-run line with judge-verified would-have-erred count. First watched category: closing.

**Steer & Send (shadow phase, 2026-07-23):** measures whether a steered regen could skip the final review glance (one-click steer→execute→send is the eventual tool). Gate (`steerSendGate.js`): deterministic checks (autosend never-list, any/changed `action_type` → ineligible, prose-only scope) then an Opus correctness verifier (steer implemented, claims grounded in context, no unrequested extras — fail-closed). Every dashboard steered regen records a `would_send` verdict to `steer_send_shadow` (flag `steersend_shadow`); nothing sends. Digest dry-run line cross-refs the closeness judge on gate-passed drafts (would-have-erred = go/no-go). Baseline going in: 32% of steered sends still diverge meaningfully (90d judge data), so live mode needs the post-verbosity-fix rate to collapse first.

**Training-signal capture (2026-06-10):** all three send paths log to `cs_ai_feedback_log` — sent/edited, `bypassed_*` (operator ignored a pending draft), `manual_*` (no draft) — plus `operator_steer` + `regen_count` columns. Historical backfill done.

**Tool Ecosystem (30+ MCP tools):** Lookup (customer, orders, products), actions (create/edit/refund orders, exchanges, wholesale orders, warehouse holds), analytics (LTV, margins, inventory, delivery estimates, reviews), knowledge (CS history search, FAQ, sizing guide).

**Dashboard (web-based):** Real-time Gorgias ticket queue with tabs (New, Follow-up, Parked, Snoozed, Closed) plus global ticket search across all statuses by customer name/email/order number/summary. Operators review AI-drafted responses and approve/edit. Operator agent for complex order manipulations. Ad Hoc Operator tab: context-free queries and actions against all CS tools (Opus, ephemeral history). Mobile-responsive PWA. Deployed on Railway at ops.rubyshines.com.

**Intake Pipeline:** Two pathways -- Gorgias ticket webhooks and Gmail CS parsing. Both feed through the AI advisor, store drafts in Supabase, and auto-assign handled tickets to "RUBIES AI" in Gorgias.

**Exchange System:** Two-phase flow. Phase 1: AI determines size, creates draft order in Shopify, shows preview with links. Phase 2: operator confirms, marks paid. Only uses FULFILLED non-cancelled orders for current size (ignores $0 exchange orders). Auto-finds correct order unless operator specifies one. Differing-items exchanges route through `exchange_difference` (read-only planning tool) — applies live volume/sale discounts to the new items per line (Shopify won't auto-apply automatic discounts to API draft orders), credits returns at actual-paid via Shopify's refund calc, and returns a recommended action: invoice (only if the operator explicitly asked to charge the difference) / auto-refund (net<0, no asking) / free exchange. Straight swaps skip it. See [exchangeMath.js](../../customer-service/lib/exchangeMath.js) + [tools/exchangeDifference.js](../../customer-service/lib/tools/exchangeDifference.js).

**Donation Routing:** After exchange, routes old items to LGBTQ+ partners. Geographic matching (Google Maps geocoding + haversine distance), load-balanced across 3 closest partners. Skips for defects. Full explanation of gender-affirming program in customer message.

**Knowledge Base (rebuilt 2026-07, corpus harvest):** 292 source-linked, trust-tagged articles (published site tier + founder-reviewed reply-corpus tier) with Voyage embeddings. Advisor searches it via the `search_knowledge` tool (kill switch: system_flag `advisor_kb_search`); weekly Monday refresh re-harvests the site, propagates amendments, and flags drifted sources for re-extraction (`customer-service/sync/refreshKb.js`). Pipeline + protocols in `customer-service/import/` (harvest, extraction, mining, triage, review sheets).

**Auto Follow-ups:** Two stages, fired by the daily sync's follow-up sweep (gorgiasAdvisorResync.js, 12:30 UTC cron) — Gorgias emits no webhook on snooze expiry, so the sweep is the real engine (a re-snooze set at ~12:35 by the sweep can miss the next day's ~12:31 pass by seconds; Stage 2 then lands a day late — known, accepted). A Haiku classifier first closes tickets that already look resolved. Stage 1: care@ via Gorgias ("just following up"), re-snoozes 3d, refreshes the dashboard conversation snapshot. Stage 2: personal jamie@ via SendGrid (quotes original response), records an internal note in Gorgias (the email itself exists only in Gmail), closes ticket, refreshes snapshot. Customer reply during snooze resets stage to 0; replies to Stage 2 stay in Gmail (intake skips them).

**Unnotified Pre-Order Outreach (auto-drafter):** Detects unfulfilled orders containing a paid item at inventory ≤ 0 whose line item lacks the `Pre-order` customAttribute. Classifies each order A/B/C, composes per-case outreach with restock ETA from variant metafields, seeds a pending CS Advisor draft via `seedOutboundDraft()`. Each candidate verified against live Warehance `ready_to_ship` before flagging. Runs as a sweep on the always-on webhook server (every 10 min), not the daily cron. See [reports/lib/unnotifiedPreOrder.js](../../reports/lib/unnotifiedPreOrder.js).

**Pre-order lifecycle tools (2026-07-16):** the recurring slip-communication loop. `preorder_hygiene` reconciles all open unfulfilled orders against live Shopify + Warehance (mirror drift, refunded-but-open, ready-but-unshipped, stuck orders, line-attribute drift; fixes are opt-in flags) and lists the waiting population by promised text. `preorder_update_notice` sends a delay wave: operator passes the promised texts + new date phrase; two variants (pre-order-only gets a swap offer, mixed gets split-or-swap), plain email from care@ via SendGrid with no upfront ticket (replies create tickets via normal intake); every candidate verified `ready_to_ship === false` in Warehance; live sends logged to `preorder_notifications` for cross-wave dedupe. dry_run → test_send → send. CLIs: `scripts/preorderHygiene.js`, `scripts/preorderUpdateNotice.js`; logic in [preOrderLifecycle.js](../../customer-service/lib/merchandising/preOrderLifecycle.js); schema `customer-service/preorder-notifications-schema.sql`.

**Operator-knowledge loop (2026-07-09):** the fix for the sweep's #1 divergence driver (~37% = facts only Jamie knew). `advisor_facts` table → active facts injected verbatim into the advisor's static prompt (`buildFactsBlock`); the daily closeness judge proposes a `candidate_fact` on factual-correction verdicts (deduped against all statuses so rejected facts never requeue); dashboard Facts panel (approve-with-edit/reject/retire, manual add goes straight active, expiry dates auto-drop perishable facts). Logic in [advisorFacts.js](../../customer-service/lib/advisorFacts.js); schema `customer-service/drafter/advisor-facts-schema.sql`.

## Key Decisions

- **Pre-order wave truth is live Shopify + Warehance, never the mirror.** Line-item `Pre-order` attributes are null in the mirror for orders last synced before 2026-05-01, mirror open/closed state drifts (the order sync only pulls open orders, so a missed fulfillment webhook never self-heals), and Warehance `ready_to_ship === false` is the only valid "waiting" signal since Shopify inventory 0 can be stock reserved on that very order. A past-dated promise whose stock arrived (reserved) is declared via `stale_targets` — operator judgment. Run `preorder_hygiene` before every wave.
- **Agentic loops, not decision trees:** Opus controls flow. All exchange/sizing/response rules live in the advisor prompt, not in code.
- **One shared tool-loop engine:** every agentic loop (advisor main+shadow, operator main+shadow, ad-hoc standalone) runs on `customer-service/lib/runToolLoop.js`; callers inject divergent behavior via callbacks (dispatch, streaming, 529/stall fallback, abort, shadow allowlist). New agents use it — don't hand-roll the call→dispatch→append loop again. (Phase 4 of the 2026-07 review, shipped 2026-07-08.)
- **Structured output:** Advisor returns `_structured` JSON alongside customer-facing markdown. Dashboard consumes structured data directly.
- **Exchange sizing from SKU, not variant title:** Last segment of SKU is the canonical size.
- **Advisor prompt changes:** Always trace execution path, read audit trails, check existing rules before modifying. Don't add rules that duplicate existing logic.
- **Operator facts are injected, not retrieved.** Approved `advisor_facts` render inline in the static prompt rather than behind a search tool — the failure mode being fixed is the advisor not knowing a fact exists, so retrieval (which requires knowing to look) can't fix it. Growth valves: Jamie's approval gate, expiry on perishable facts, dedupe-on-propose, and a retrieval fallback only if the set ever exceeds ~200 facts. Facts state durable business truths; live data (inventory, order state, rates) stays tool-fetched and wins on conflict.
- **A wrong operator fact cannot be fixed with a prompt rule — check `advisor_facts` before writing one.** Facts outrank KB search by design (precedence above), so an advisor holding an inaccurate fact answers confidently and never searches. Measured 2026-08-05: a fact asserting the foam chest pad set "comes in sets of three" produced wrong product comparisons at 0/3 against two different placements of a new grounding rule, and went right as soon as the fact was corrected. The corollary is a three-layer sweep whenever the advisor states something wrong and confident about a durable fact: correct the fact, re-extract the KB candidate (`loadKbCandidates.js` + `rebuildKnowledgeBase.js` — the weekly refresh re-harvests `kb_sources` but only FLAGS drifted candidates, it never re-extracts them), and fix the source-of-truth copy on the site, or the next harvest reintroduces the contradiction. Facts also have to be SYMMETRIC across products the advisor will compare: giving one product a precise structure and its sibling none leaves a gap the model fills by inventing a contrast, and a fact forbidding the invented phrasing measured identical to no fact at all (2/6 either way). The fix is a parallel positive fact on the sibling, which took the same case to 0/6.
- **Always check stored ticket data** in Supabase before diagnosing advisor issues on a ticket.
- **Diagnosing a flagged draft: find the cause before reaching for a lever (2026-08-04).** Four causes, four different fixes. (a) The advisor didn't *know* something only Jamie knows → propose an `advisor_facts` entry, not a rule; this is the largest cluster (~37%). (b) The prompt told it to do the wrong thing → fix or delete that rule; a founder audit of 62 wording mandates found 8 he did not want, including one that had the advisor create orders on a guess. (c) The prompt told it the right thing and it did not comply → grep the prompt FIRST; 7 of 11 drafts Jamie flagged were violating rules already written down, some marked CRITICAL, so another rule would not have helped and the fix is removing competing instructions. (d) A tone sample contradicts a rule → fix the sample, not the rule. Before any of it, read `draft_history[0]`, never `draft_response` — on a steered ticket the stored draft is the model obeying Jamie's correction and hides the defect entirely. And one draft is a hypothesis, not a finding: measure the pattern against the **unfiltered** population before changing anything. A rate computed only on steered or edited drafts is biased by construction — "Jamie overrides the nudge 67% of the time" was true of steered drafts and false overall; he agrees with it 92% of the time.
- **Advisor quality metrics count only drafts the advisor wrote, and an unedited send is not approval (2026-08-04).** `cs_ai_drafts` holds every outbound message: `auto_follow_up` is a fixed template (~97% byte-identical, and all of it lands at turn 4+), `operator_reply` and `manual_send` are Jamie composing from scratch — stored into *both* `draft_response` and `sent_response`, so each scores as a flawless untouched draft — and `simulator` is test traffic. Any quality metric must filter to `source='poller'` + `draft_kind='advisor_draft'`; leaving them in understated the digest edit rate by ~5 points and put 43 non-advisor messages into the judge's verdicts. Separately, Jamie often ships drafts he would not have written rather than spend time rewriting: measured at **~28% of unedited sends**. So an unedited send is an *unlabeled* sample, not a positive one, and the true "right as sent" rate is roughly two-thirds of whatever the unedited rate reports.
- **Testing workflow:** Pull real conversations from Supabase, run tests directly via node (not MCP).
- **Gorgias writes before Supabase writes:** Call Gorgias first and let errors propagate; only update `cs_tickets` after Gorgias confirms. Never wrap the Gorgias call in try/catch — that causes silent split-brain between the two systems.
- **Drift sync auto-resolves noise, reports real misses, never backfills drafts:** the daily reconciler (`gorgiasAdvisorResync.js`) triages each drift ticket via `driftTriage.js` — duplicates, emoji-reaction reopens, and vendor/sales spam are auto-closed (with an audit note); genuine customer misses are surfaced in the digest but deliberately NOT auto-drafted, so intake/webhook bugs stay visible. CLI `--execute` is the manual path that also drafts the real misses; dry runs stay pure detection.
- **message_type taxonomies are separate:** `cs_tickets.message_type` is the canonical inquiry category (10-value list in [lib/messageTypes.js](../../customer-service/lib/messageTypes.js)). `intake_state.message_type` (inside structured_output JSONB) is a separate sub-taxonomy for sizingEngine item-level decisions. Don't conflate — non-canonical values coerce to `uncategorized`.
- **Related ticket injection:** contextBuilder pulls the most-recent closed exchange/refund/defect ticket (60d window) with a populated `history_summary`; advisor injects it as `[PRIOR TICKET]`. Legacy tickets without a summary are excluded. No lazy summary generation.
- **Auto follow-ups run from the daily sweep; dedup by `follow_up_stage`.** The `ticket-updated` webhook path exists but Gorgias sends no event on snooze expiry, so in practice every stage fires from the 12:30 UTC sweep (verified 2026-07-08: all sends since May at 12:3x UTC). Stage advances atomically on `cs_tickets.follow_up_stage` (guarded UPDATE, PR #59); customer replies reset to 0. Stage 1 sent as AI bot so intake skips it; Stage 2 closes the ticket. Follow-up sends refresh the conversation snapshot and Stage 2 leaves an internal note in Gorgias — without these the dashboard showed snoozed tickets as untouched (2026-07-08 confusion).
- **Tool calls precede customer-facing prose.** The advisor saves only the last round's text blocks, so prose written before a tool call is dropped. Rule: planning narration before tool calls is fine, but the customer-facing email must be written entirely in the final round after all tool results. Same rule applies to the operator agent.
- **Outbound-initiated tickets are modeled as snoozed-after-reply.** `status='snoozed'`, `initiated_by='operator'`, `has_agent_reply=true`; seeded draft with `source='operator_outreach'`, `status='sent'`, empty `draft_response`, `sent_response=body`. Normal snooze-expiry follow-up plumbing applies with no extra state. See [customerOutreach.js](../../customer-service/lib/customerOutreach.js).
- **Single-draft outreach stages with NULL `gorgias_ticket_id`; Gorgias created lazily on send.** `create_outreach_ticket` composes one Opus draft and seeds `cs_tickets`/`cs_ai_drafts` rows with null Gorgias id. On send, `apiSendDraft` creates the Gorgias ticket and back-fills both rows. Use for single bespoke drafts needing review before any external write; use `sendIncidentOutreach` for batch sends. Outreach drafts can carry a paired operator action: when the steer describes an operation, the composer proposes `action_type` + `operator_action_summary` and the draft stages with the dashboard action panel / Execute & Send active, same as inbound drafts.
- **Per-incident outreach pattern: durable substrate + one-off driver.** Build a per-incident driver in `scripts/_<incident>-outreach.js` and hand the order list to `sendIncidentOutreach()` ([customerOutreach.js](../../customer-service/lib/customerOutreach.js)). Handles Gorgias creation, pipeline registration, snooze, and `order_alert_notes`. Modes (flags, not env vars): default print-only, `--test-send`, `--send`. The driver + template is one-off; the outreach infrastructure is permanent.
- **Operator note overrides pre-order auto-classification in the daily report.** An unresolved operator note pulls an order out of the silent Pre-Orders bucket into actionable/waiting flows. Implemented in [reports/dailyOrderAlerts.js:236](../../reports/dailyOrderAlerts.js#L236).
- **`order_alert_notes.alert_type` records intake pipeline, not state-kind.** Values: `'unfulfilled'`, `'shipping'`. Don't introduce values for operator states — use note text and Gorgias tags instead.
- **Completed operator actions are filed inline in the ticket timeline; the agent sees the ticket-level union.** Each completed action appends to `cs_ai_drafts.actions[]` (append-only JSONB) with `executed_at`, `action_type`, `summary`, `links`. Dashboard weaves these chronologically as non-interactive yellow blocks. Because each customer reply creates a fresh draft row, anything reading "what was already done" must union `actions[]` across ALL the ticket's drafts (`unionTicketActions` in dashboard/server.js) — the operator agent's prompt and the timeline both do. `action_result` is the in-flight scratchpad: cleared on completion (unless the same turn staged a new awaiting-confirmation preview) and on terminal draft events (send/release/delete/spam). The Yes/No confirm buttons key off the server-computed `chat_pending_preview` flag inside it — never off client-side regex.
- **Pre-order detection reads Shopify line item customAttributes, not just product tags.** The Pre-Order Now app stamps each line item with a `Pre-order` customAttribute containing the target date. Tag alone misses historical orders where the tag was removed after the window closed — the line item attribute persists.
- **Help-center FLOW transcripts are parsed directly.** Gorgias flow messages pack the whole interaction into one help-center message with `meta.origin==='flow'`. `extractCleanBody` detects the flow marker and parses via `cleanHelpCenterBody` (drops bot copy, keeps customer input). Direct help-center messages that use `>` quoting keep the normal reply-parser path.
- **The operator's message view must show at least what the advisor read (2026-08-05).** Gorgias hands us two versions of every customer email and they disagree: `stripped_html` (stored as `body_html`, rendered to the operator) against the plain text (stored as `body`, read by the advisor). Gorgias's stripper cuts trailing lines and Outlook sends HTML fragments, so the operator was silently getting the shorter one — a customer named the product they wanted on its own bold line, it survived only in the plain text, and the ticket read as "could I get this instead?" with no antecedent while the advisor had correctly drafted the exchange. [messageBody.js](../../customer-service/dashboard/public/messageBody.js) compares the two line by line and renders plain text whenever the HTML is missing substantive content; losing formatting is always cheaper than hiding words the advisor acted on. The threshold was tuned by replaying the rule over every stored customer message (4.4% fall back), not against the one ticket that surfaced it — a length-ratio rule tuned on that ticket alone would have missed it entirely at 93% length parity.
- **Duplicate auto-close: first contact only, and continuations are transplanted, never closed away.** `checkForDuplicateTicket` returns null once a ticket has a second customer message (2026-06-10 incident). A first-contact ticket that *advances* an existing conversation (a reply that failed to thread — masked addresses, fresh compose) is a `continuation`, not a duplicate: the message is moved onto the surviving ticket as a real customer message (fires the message webhook → advisor drafts there), the stray closes with pointer notes, and the survivor's follow-up cycle resets. `close_new` is reserved for true retries that add nothing (2026-07-07 incident: six customers' unthreaded replies were closed as "duplicates", robo-nudged twice, then auto-closed). Ordering is load-bearing: transplant before reopening the survivor, or the snooze-expiry webhook fires a Stage 1 nudge. See [ticketContinuation.js](../../customer-service/lib/ticketContinuation.js).
- **Gmail intake claims its row atomically.** Pub/Sub is at-least-once; `processMessage` does a conditional `UPDATE email_messages SET processed_at = NOW() WHERE processed_at IS NULL` as its first action — only one concurrent caller wins. Secondary defense: checks Gorgias for existing open tickets by email.
- **Default shipping speed is `standard` across all order-creation tools.** `create_order`, `create_invoice_order`, `create_exchange_order`, `create_wholesale_order` all default to `standard`. Operator must explicitly pass `shipping_speed: "expedited"` to upgrade.
- **`update_shipping_speed` works on Shopify drafts and placed Warehance orders.** Pass a draft name like `"D6720"` (string with leading D) for draft updates; numeric input hits Warehance. Refuses when the draft is `COMPLETED`.
- **All order-creation tools accept an explicit `shipping_address` override.** Beats the customer default address and (for exchanges) the original-order address. Shared helper in [orderUtils.js](../../customer-service/lib/orderUtils.js).
- **Wholesale lines set a custom `priceOverride`, never a discount.** A fixed-amount discount on a foreign-currency draft is not locked — Shopify reconverts it at checkout, so the amount the customer pays diverges from the invoice (percentage discounts lock; fixed-amount don't). A custom line price locks at the draft's fixed FX rate like a catalog price and keeps the variant link, guaranteeing invoice = checkout in every currency and payment method. Order-profitability revenue is computed net of line discounts (`unit_price` is gross) so legacy discount-based orders don't overstate margin.
- **CS comp codes append to per-level "Thank You N" bucket discounts, never "Welcome".** One shared discount per percent level; each issued code is added to it so the admin discounts list stays at one entry per level. Shopify's `usageLimit` on a multi-code discount applies per code (verified live against the Klaviyo Welcome 10), keeping every code single-use. "Welcome" titles are reserved for the Klaviyo/SMS signup discounts. Discount titles are admin-only — customers see only the code they typed. Free-product comps stay one-discount-per-code. **Corollary for anything that invalidates a code: our discounts are code POOLS** (10k bulk birthday codes, 1.2k free-swimwear, the shared "Thank You N" buckets), so revocation must target the individual redeem code, never the discount node — deleting or deactivating the node breaks every other customer holding a code on it. `revoke_discount_code` deletes the redeem code on pooled discounts and only falls back to deactivating the node when the discount owns exactly one code.
- **Ad Hoc Operator PDF handling: extract text server-side, native fallback for image-only PDFs.** `POST /api/console/extract-pdf` runs `pdf-parse` v2; text-extracted PDFs inline as text; PDFs with <200 chars extracted fall back to a native Anthropic `document` block (cap 20 pages, 5 MB upload cap).
- **Operator agent hard-stops on infrastructure errors.** Distinguish infrastructure errors (GraphQL errors, 5xx, stack traces, fetch failures) from business-outcome errors (order not found, OOS). Infrastructure errors → reply once with error excerpt and stop; no workaround attempts.
- **`consolidate_orders` merges two unfulfilled orders without cancel/refund.** Adds dropped order's items to keeper at 100% discount, placeholder-fulfills dropped order, refunds shipping if combined subtotal meets threshold. Two-phase preview/confirm. Refuses on partial-fulfillment, Warehance `in_progress`, or different customers. See [consolidateOrders.js](../../customer-service/lib/tools/consolidateOrders.js).
- **`split_shipment` merge mode (`ship_with_order`) prevents double-boxing.** When in-stock items from an unfulfilled order are folded into a new (usually free) order so everything leaves in one box, it placeholder-fulfills them on the source (no new pre-order created) and cross-notes both orders. The 3-step recipe lives in the create_order / split_shipment tool descriptions.
- **Unnotified pre-order outreach is detection + outreach, not channel blocking.** Unpublishing from Shop channel hides all variants including in-stock ones, so we detect and stage outreach instead. Detection runs on the daily cron to avoid racing Warehance allocation. Idempotent via an `author='auto'` unresolved `order_alert_notes` row with a 14-day staleness guard.
- **`action_type` taxonomy is operator-write verbs, mostly 1:1 with tools.** Values: `exchange` / `refund` / `exchange+refund` / `free_order` / `order_modification` / `warehouse_hold` / `cancellation` / `customer_profile_update` / `discount_code` / `split_shipment` / `order_consolidation` / `invoice_kept_items`. Adding a new action_type requires: matching MCP tool in `operatorTools.js`, whitelist in `aiAdvisor.js parseStructured`, and dashboard prefill in `app.js`.
- **Operator agent confirmation handling: tool call mandatory, never re-preview.** On any confirm signal, the agent's next action MUST be the same tool from the phase-1 preview with `confirmed: true`. Never re-show the preview or narrate. A confirmation scopes to the most recent STILL-PENDING preview (an intervening Q&A doesn't kill it); executed or cancelled previews are dead and never re-fire.
- **Any change to an UNFULFILLED order freezes it with a warehouse hold before it can ship.** This is the governing policy for unshipped-order edits. ALL item modifies (change/add/remove/swap) route to `action_type: warehouse_hold` — vague AND specific (the prior "specific request → skip the hold, go straight to order_modification" carve-out left orders exposed to shipping the wrong item before an operator executed the swap). For specifics the advisor also stages the change in `operator_action_summary` for the operator to execute then release. ALL cancels hold too (2026-07-17): ambivalent/no-reason cancels route to `warehouse_hold` (save-the-sale; a firm cancel with NO stated reason is still ambivalent — firmness alone never skips the hold), and clear cancels (`action_type: cancellation`) get a protective hold at intake + backstop sweep that lands in `actions[]` WITHOUT setting `action_executed_at` (which tracks the cancel itself), covering the window until the operator executes. Address-changes-without-an-address also hold. **The advisor's `action_type` choice is what gates the safety net:** `reconcilePendingHolds` only sweeps drafts whose `action_type` is `warehouse_hold` or `cancellation`, so an advisor that labels an unshipped-order edit `order_modification` produces neither a hold nor a backstop, and the order can ship wrong. `order_modification` is therefore reserved for exactly one case — a same-country address change — and the prompt states that scoping explicitly at the top of the section (2026-07-28; before that the two action types sat adjacent as apparent equals and the advisor picked wrong on ~20–60% of steered-redirect cases). Preserve that scoping statement in any future edit to the section.

The address is validated (geocode plausibility), never rewritten — Google's normalization can drop unit numbers.

Previously a dead field nothing read; now the channel for surfacing auto-action fallbacks (e.g. an address change that couldn't auto-apply) so an operator fixes the reply before sending.
- **Advisor-proposed warehouse holds execute at intake (best-effort), with a backstop sweep that guarantees the hold lands.** `autoExecuteAdvisorHold` in processGorgiasTickets.js attempts the hold synchronously at intake when `action_type` is `warehouse_hold` OR `cancellation` (protective) and files the result in `draft.actions[]`. This attempt commonly fails because the order isn't queryable in Warehance yet (the customer chats to edit/cancel minutes after ordering, before ingestion); failures are recorded on `draft.audit_trail`, not swallowed. The guarantee comes from `reconcilePendingHolds` ([lib/holdReconcile.js](../../customer-service/lib/holdReconcile.js)), a sweep on the always-on webhook server (every 3 min) that places any proposed-but-unexecuted hold once the order appears in Warehance — idempotent, bounded to open tickets in the last 3 days, and giving up (audit marker, NOT a false `action_executed_at`) when the order is already in fulfillment. (Both paths were silently inert until 2026-06-16 — `handleWarehouseHold` was never exported from orderNotes.js, so both destructured `undefined` and every automatic hold threw; until then holds only landed when an operator placed them by hand.) `holdAlreadyPlaced` in operatorAgent.js reads executed actions only (ticket-level union, release-aware — the most recent hold/release action wins) — `draft.action_type` is a proposal, not an execution. Both hold paths resolve their target via shared `holdTargetOrderNumber()`: the advisor's structured `action_order_number` (declared explicitly when a steer or the customer redirects the action to a different order than the loaded context) wins over the draft's ticket-linked `order_number`, which echoes loaded context and is the wrong target after a redirect (2026-07-21 ticket: hold landed on an already-shipped order). `handleWarehouseHold` refuses fulfilled/cancelled orders with error text the sweep classifies as give-up — Warehance otherwise accepts a meaningless hold flag on shipped orders, turning the designed loud failure into silent false success.

- **Model swaps are qualified by scenario-suite-plus-control, not shadow eval.** `scripts/modelSwapEval.js --candidate <model> --repeat 3` runs the pinned suite against a candidate, automatically re-runs every failure against the incumbent, and reports accuracy + latency + cost (from `ai_calls`) with an adopt/reject verdict.
