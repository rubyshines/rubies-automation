## What's Built

**AI Advisor (Opus-based):** AI reads full conversation + calls tools as needed. Handles exchanges, sizing, shipping, product questions, positive feedback. Returns structured JSON for dashboard consumption (including `message_type`, `customer_sentiment`, `summary`, `history_summary`). All business rules live in the system prompt. Injects recent related exchange/refund/defect tickets via history_summary for second-round follow-up context.

**Tool Ecosystem (30+ MCP tools):** Lookup (customer, orders, products), actions (create/edit/refund orders, exchanges, wholesale orders, warehouse holds), analytics (LTV, margins, inventory, delivery estimates, reviews), knowledge (CS history search, FAQ, sizing guide).

**Dashboard (web-based):** Real-time Gorgias ticket queue with tabs (New, Follow-up, Parked, Snoozed, Closed) plus global ticket search across all statuses by customer name/email/order number/summary. Operators review AI-drafted responses and approve/edit. Operator agent for complex order manipulations. Mobile-responsive PWA. Deployed on Railway at ops.rubyshines.com.

**Intake Pipeline:** Two pathways -- Gorgias ticket webhooks and Gmail CS parsing. Both feed through the AI advisor, store drafts in Supabase, and auto-assign handled tickets to "RUBIES AI" in Gorgias.

**Exchange System:** Two-phase flow. Phase 1: AI determines size, creates draft order in Shopify, shows preview with links. Phase 2: operator confirms, marks paid. Only uses FULFILLED non-cancelled orders for current size (ignores $0 exchange orders). Auto-finds correct order unless operator specifies one.

**Donation Routing:** After exchange, routes old items to LGBTQ+ partners. Geographic matching (Google Maps geocoding + haversine distance), load-balanced across 3 closest partners. Skips for defects. Full explanation of gender-affirming program in customer message.

**Knowledge Base:** 63 embedded articles (Voyage AI, 512 dims). Semantic search for product info, shipping, policies. NOT used for exchange decisions (advisor handles those directly).

**Auto Follow-ups:** Event-driven off Gorgias snooze expiry. Stage 1: care@ via Gorgias ("just following up"), re-snoozes 3d. Stage 2: personal jamie@ via SendGrid (quotes original response), closes ticket. Customer reply during snooze resets stage to 0; replies to Stage 2 stay in Gmail (intake skips them).

**Unnotified Pre-Order Outreach (auto-drafter):** Detects unfulfilled orders containing a paid item at inventory ≤ 0 whose line item lacks the `Pre-order` customAttribute — i.e. the customer bought a continue-selling OOS item (typically via Shop App, which bypasses the Pre-Order Now theme) without ever being told it's a pre-order. Classifies each order A/B/C (only-leak / leak+in-stock / leak+other-OOS), composes per-case outreach with restock ETA from variant metafields, reuses the advisor's `compare_products` for swap suggestions, and seeds a pending CS Advisor draft via `seedOutboundDraft()`. The Shopify `available ≤ 0` signal is only a cheap pre-filter — each candidate is then verified against live Warehance stock and an item is flagged only if genuinely `backordered > 0`, so fully-committed-but-in-stock hot SKUs (which show 0 available yet ship fine) don't generate false outreach. Runs inside the daily order alerts cron; results surface in the "Drafted in CS Advisor (auto)" report section. See [reports/lib/unnotifiedPreOrder.js](../../reports/lib/unnotifiedPreOrder.js).

## Key Decisions

- **Agentic loops, not decision trees:** Opus controls flow. All exchange/sizing/response rules live in the advisor prompt, not in code.
- **Structured output:** Advisor returns `_structured` JSON alongside customer-facing markdown. Dashboard consumes structured data directly.
- **Exchange sizing from SKU, not variant title:** Last segment of SKU is the canonical size.
- **Advisor prompt changes:** Always trace execution path, read audit trails, check existing rules before modifying. Don't add rules that duplicate existing logic.
- **Always check stored ticket data** in Supabase before diagnosing advisor issues on a ticket.
- **Testing workflow:** Pull real conversations from Supabase, run tests directly via node (not MCP).
- **Gorgias writes before Supabase writes:** when a CS action closes/snoozes/updates a ticket, call Gorgias first and let errors propagate. Only update `cs_tickets` after Gorgias confirms. Never wrap the Gorgias call in try/catch to "protect" the Supabase update — that causes silent split-brain between the two systems.
- **Drift sync is a diagnostic, not a fixer:** `gorgiasAdvisorResync.js` exists so Jamie can spot sync issues and fix the underlying bug in intake/advisor code. Never schedule it in production or use it to backfill around bugs — fix the source.
- **message_type taxonomies are separate:** `cs_tickets.message_type` is the canonical inquiry category, validated against the 10-value list in [lib/messageTypes.js](../../customer-service/lib/messageTypes.js). `intake_state.message_type` (inside structured_output JSONB) is a separate sub-taxonomy used internally by sizingEngine for item-level action decisions. Do not conflate — the write paths coerce non-canonical values to `uncategorized`.
- **Related ticket injection:** contextBuilder pulls the single most-recent closed exchange/refund/defect ticket for the customer (60d window) with a populated `history_summary`, and the advisor injects it as a `[PRIOR TICKET]` block in the user message. Legacy tickets without a summary are intentionally excluded from the Related Ticket dashboard panel; they still appear in Past Tickets. No lazy summary generation — only tickets already processed by the advisor with the top-level history_summary field surface.
- **Auto follow-ups are event-driven, dedup by `follow_up_stage`.** Trigger is the Gorgias `ticket-updated` webhook firing on a snoozed→open transition (snooze expired, no customer reply). Stage 0→1 and 1→2 advance based on `cs_tickets.follow_up_stage` (ticket-level), not on draft state. Stage 1 reply is sent as the AI bot user so intake skips it; Stage 2 closes the ticket and replies to it stay in Gmail. New customer messages reset `follow_up_stage` to 0. Never re-introduce a polling timer — the snooze expiry event is the source of truth.
- **Tool calls precede customer-facing prose.** The advisor's agentic loop saves only the last round's text blocks, so any greeting-prefixed prose written before a tool call is dropped from the saved draft. Steered drafts trigger this most often because the steer hands the model the substance of the reply. Rule (in the advisor system prompt): planning narration is encouraged before tool calls (it surfaces in the operator's reasoning trace via `splitThinkingFromDraft`), but the customer-facing email must be written entirely in the final round after all tool results are in. Same rule applied to the operator agent.
- **Outbound-initiated tickets are modeled as snoozed-after-reply.** Operator-initiated outbounds (e.g. `customerOutreach.sendIncidentOutreach()`) create a `cs_tickets` row with `status='snoozed'` + `initiated_by='operator'` + `has_agent_reply=true`, a seeded `cs_ai_drafts` row with `draft_kind='advisor_draft'` + `source='operator_outreach'` + `status='sent'` + empty `draft_response` (we've already sent — nothing to draft until customer replies) + `sent_response=body` (audit), and snooze the Gorgias ticket 3 days. The existing snooze-expiry → Stage 1 (day 3) → Stage 2 (day 6) follow-up plumbing applies with no additional state. When the customer replies, normal intake upserts on `gorgias_ticket_id` and the row transitions to `status='open'` naturally. Test-send mode skips all durable writes — only live mode registers with the pipeline.
- **Single-draft operator outreach stages with NULL `gorgias_ticket_id`; Gorgias is created lazily on send.** Distinct from `sendIncidentOutreach` (batch send, Gorgias + snooze created up front). The `create_outreach_ticket` MCP tool composes one draft via Opus given an order + free-form steer (see [composeOutboundDraft.js](../../customer-service/lib/composeOutboundDraft.js)), then `seedOutboundDraft()` writes a `cs_tickets` row with `gorgias_ticket_id=null` + `status='open'` + `initiated_by='operator'` + `message_type='proactive_outreach'` and a `cs_ai_drafts` row in `status='pending'` + `source='operator_outreach'`. Nothing external happens until the operator clicks send in the dashboard, at which point [apiSendDraft](../../customer-service/dashboard/server.js) detects the null id, calls `gorgias.createOutboundTicket`, and back-fills `gorgias_ticket_id` on both rows. Use this pattern when a single bespoke draft needs human review before any external write; use `sendIncidentOutreach` when batch-sending across many orders with a pre-approved template body. Schema requirement: `cs_tickets.gorgias_ticket_id` and `cs_ai_drafts.gorgias_ticket_id` are nullable (NULLs remain distinct under the unique constraint).
- **Outbound tickets persist `order_context` from the order mirror.** Operator-initiated tickets (proactive outreach, single-draft `create_outreach_ticket`, auto unnotified-pre-order outreach) never run through the inbound advisor, which is the only thing that normally writes `cs_tickets.order_context`. Without it the dashboard showed "No order associated" until an async customer-context fetch landed. `buildOrderContextFromMirror()` in [customerOutreach.js](../../customer-service/lib/customerOutreach.js) builds the `{name, date, fulfillment_status, items}` shape (matching the inbound advisor's `structured.order` and what `renderOrderCard` consumes) from `orders` + `order_line_items`, and is called by `seedOutboundDraft` and `registerOutboundWithAdvisorPipeline`. Dashboard render also bypasses the bot-intake collapse for `initiated_by='operator'` tickets — they have no chatbot intake to hide, so the whole thread renders plainly.
- **Per-incident outreach pattern: durable substrate + one-off driver.** When an unexpected issue (sold-out item shown as pre-order, defect batch, shipping incident) or a proactive campaign (post-purchase feedback) requires emailing customers and tracking replies: build a per-incident driver in `scripts/_<incident>-outreach.js` that identifies affected orders and composes per-order email bodies, then hand the list to `sendIncidentOutreach()` in [customer-service/lib/customerOutreach.js](../../customer-service/lib/customerOutreach.js). The module handles Gorgias creation, advisor-pipeline registration (see preceding decision), Gorgias snooze, and `order_alert_notes` insertion. Three modes via flags (no env vars): default print-only, `--test-send` (real Gorgias tickets to a test address, no durable writes), `--send` (live). Affected orders surface in the daily report's "Waiting on Response" via the unresolved note. Resolution: operator agent calls standard `resolve_order` after handling the customer's reply. The per-incident *driver script + email template* is one-off; the *outreach + tracking infrastructure* is permanent. Reuse for: out-of-stock incidents (a few times a year), defect outreach, post-purchase feedback campaigns on new products.
- **Operator note overrides pre-order auto-classification in the daily report.** [reports/lib/unfulfilled.js classifyPreOrder](../../reports/lib/unfulfilled.js) flags any order with a `Pre-order` line item attribute or matching tag as `isPreOrder=true`, which would normally route it into the silent Pre-Orders bucket. But when an operator has explicitly added an unresolved note (e.g. mistaken-preorder outreach, defect outreach), the order needs to surface in actionable/waiting flows. Bucket filters in [reports/dailyOrderAlerts.js:236](../../reports/dailyOrderAlerts.js#L236) implement this precedence — an unresolved operator note pulls the order out of Pre-Orders into the actionable/waiting/resolved flow.
- **`order_alert_notes.alert_type` records intake pipeline, not state-kind.** Existing values: `'unfulfilled'` (from unfulfilled checker), `'shipping'` (from shipping delays). It is not a per-state semantic tag. Don't introduce values like `'awaiting_customer_decision'` to flag operator states — that conflates pipeline-source with state-kind on one column. Distinguish operator-flagged states via note text (visible in the daily report row) and Gorgias ticket tags (filterable in inbox), NOT via new alert_type values. If a future need genuinely requires a state-kind dimension, add a separate column rather than overloading `alert_type`.
- **Completed operator actions are filed inline in the ticket timeline.** Each completed action appends an entry to `cs_ai_drafts.actions` (append-only JSONB) with `executed_at`, `action_type`, `summary`, and `links`. The dashboard weaves these chronologically into the conversation thread as non-interactive yellow blocks, so reading the ticket top-to-bottom matches real chronology. The bottom action panel only shows fresh advisor proposals or in-progress chat — never replays historical actions. `action_result` remains the in-flight scratchpad and is cleared on completion.
- **Pre-order detection reads Shopify line item customAttributes, not just product tags.** The Pre-Order Now app stamps each ordered line item with a `Pre-order` attribute whose value is the customer-visible target string (e.g. "Target availability end of June, 2026."). [fulfillmentChecker.js](../../customer-service/lib/tracking/fulfillmentChecker.js) treats either a line item attribute OR a product tag as a pre-order signal, and surfaces the per-item target date so the advisor can branch on future-target vs past-due-still-zero vs past-due-resolved. Product tags alone miss the common case where a customer ordered during a pre-order window that has since closed — the tag was removed but the line item attribute persists on the historical order.
- **Help-center FLOW transcripts are parsed directly, not through the reply-parser.** Gorgias Convert/Automate flows ("Change my order before it ships", Returns/Exchanges, product selector) pack the whole interaction into ONE help-center message with `meta.origin==='flow'`: bot prompts plus the customer's choices and free-text as `>`-prefixed lines, and an empty `stripped_text`. The empty-stripped fallback in [extractCleanBody](../../customer-service/intake/processGorgiasTickets.js) runs the email-reply-parser, which treats `>` as quoted-reply markers and deletes every customer line — storing bot-prompts-only and feeding that to the advisor. `extractCleanBody` now detects `meta.origin==='flow'` and parses the transcript via `cleanHelpCenterBody` (drops bot copy/button labels/order-display lines, keeps the customer's request). Gated on the flow marker so direct help-center messages that legitimately quote prior content with `>` keep the normal path. The fix is data-driven — it parses whatever transcript Gorgias sends, so editing/adding flows in Gorgias never breaks it and the flow definitions never need to be mirrored into our code.
- **Gmail intake claims its row atomically and checks Gorgias before forwarding.** Gmail Pub/Sub delivers at-least-once, so concurrent webhook deliveries on the same `gmail_message_id` used to create duplicate Gorgias tickets — both runs passed dedup checks before either had committed state, then both called `gorgias.createTicket`. [processGmailCs.js](../../customer-service/intake/processGmailCs.js) processMessage now does a conditional `UPDATE email_messages SET processed_at = now WHERE processed_at IS NULL` as its first action; only one concurrent caller wins the row. As a secondary defense it also calls `gorgias.findOpenTicketsByEmail` to skip when Gorgias's native email integration is also handling the message.
- **Default shipping speed across all order-creation tools is `standard`.** `create_order`, `create_invoice_order`, `create_exchange_order`, and `create_wholesale_order` all default to `shipping_speed: "standard"` for every destination. Previously [wholesaleOrder.js](../../customer-service/lib/tools/wholesaleOrder.js) defaulted to `expedited` for non-US wholesale (FedEx routing); that asymmetric default is gone — the agent never silently ships faster than the operator asked for. Operator must explicitly pass `shipping_speed: "expedited"` to upgrade. Standard maps to the free zone-appropriate Shopify rate (US Standard / Free Canada Standard / Free International / Free DDP); expedited adds the FedEx / Expedited International routing.
- **`update_shipping_speed` works on Shopify drafts and placed Warehance orders.** Pass a draft name like `"D6720"` (string with leading D) → tool routes to [draftOrderUpdate](../../customer-service/lib/shopify.js) and retitles the `shippingLine` via `getShippingMethodTitle(country, speed)`. Numeric input hits Warehance first; if not found, falls back to `D<num>` lookup before reporting "not found". Refuses when the draft is `COMPLETED` (already a real order — use the order number instead). No-ops when the draft is already on the requested speed. This unifies the "fix shipping on a draft I just created" and "upgrade a placed order" flows behind one tool.
- **All order-creation tools accept an explicit `shipping_address` override.** `create_wholesale_order`, `create_invoice_order`, `create_exchange_order`, and `create_order` all expose a shipping address parameter that beats the customer default address and — for exchanges — the original-order address. The merge helper [applyShippingAddressOverride](../../customer-service/lib/orderUtils.js) and the shared [SHIPPING_ADDRESS_OVERRIDE_SCHEMA](../../customer-service/lib/orderUtils.js) fragment in `orderUtils` keep the four tools consistent (snake_case fields in, camelCase DraftOrderInput out). Use whenever the customer has asked to ship somewhere different from what's on file — the customer record is often not updated yet. Without this override the agent silently used Shopify's `defaultAddress` and customer requests for a new ship-to were lost.
- **Ad Hoc Operator PDF handling: extract text server-side, native fallback only when extraction is empty.** PDF attachments in the Ad Hoc Operator console route through `POST /api/console/extract-pdf` ([apiConsoleExtractPdf](../../customer-service/dashboard/server.js)) which runs `pdf-parse` v2 server-side. Text-extracted PDFs (the common case — invoices, exported spreadsheets, generated reports) are inlined into the prompt as a normal text attachment, costing roughly tokens-per-visible-char. PDFs with <200 chars of extractable text (scanned/image-only) fall back to a native Anthropic `document` content block, capped at 20 pages. Raw upload cap is 5 MB. Don't replace this with a regex/CSV-parsing layer — pdf-parse text plus Opus reading is sufficient for tabular invoices.
- **Operator agent hard-stops on infrastructure-error tool results.** The operator system prompt distinguishes infrastructure/bug errors (GraphQL errors, undefined fields, exceptions, stack traces, ECONNREFUSED, HTTP 5xx, fetch failures) from business-outcome errors (order not found, SKU mismatch, already fulfilled, invalid input). Infrastructure errors → reply once with the failing tool name + error excerpt and stop, no workaround attempts. Business errors → try a different tool/query. When ambiguous, default to stopping. Rationale: working around a broken substrate compounds the problem and burns user trust faster than a single wasted turn.
- **`consolidate_orders` merges two unfulfilled orders for the same customer without cancel/refund.** New tool ([consolidateOrders.js](../../customer-service/lib/tools/consolidateOrders.js)). Adds the dropped order's items onto the keeper at 100% discount (already paid on the dropped order), placeholder-fulfills the dropped order so the warehouse stops processing it, tags both orders with cross-references, and — if the combined product subtotal (pre-merge) meets the keeper destination's `shipping_zones.free_shipping_threshold` — refunds the shipping fee paid on each order with tax. Two-phase preview/confirm. Refuses on partial-fulfillment of the dropped order, on Warehance `in_progress` on either side, or on different customers. Distinct from `cancel_order` (which would refund the dropped order entirely) and `edit_order` (single-order edits only).
- **Unnotified pre-order outreach is detection + outreach, not channel blocking.** Shop App buyers can purchase continue-selling OOS variants without seeing pre-order messaging because Shop App ignores the custom theme. The fix considered (and rejected) was unpublishing affected products from the Shop sales channel — Shopify publication is product-level only, so unpublishing a product to stop one OOS variant also hides its in-stock variants, losing more Shop revenue than the leak costs. Instead the auto-drafter detects the leak orders post-hoc and stages operator-reviewed outreach. Detection runs on the daily cron (not the order webhook) on purpose: a real-time hook would race Warehance allocation and false-positive on orders that actually ship fine. Idempotent via an `author='auto'` unresolved `order_alert_notes` row; 14-day staleness guard skips orders that predate the drafter. Detection is channel-agnostic — the signal is inventory + missing line-item attribute, not `source_name` — so Online Store race conditions are caught too.
- **`action_type` taxonomy is operator-write verbs, mostly 1:1 with tools.** Each `action_type` value names a concrete write the operator (or operator agent) must execute. Most map 1:1 to a single MCP tool, but the same tool may serve multiple classifications when the underlying write is identical and the distinction is purely semantic for reporting (e.g. `create_exchange_order` produces a $0 draft for both `exchange` and `free_order` — the difference is whether there's an item-being-returned story). The vocabulary today: `exchange` / `refund` / `exchange+refund` (`create_exchange_order`, `refund_order`), `free_order` (`create_exchange_order` with no return story — refunded customer picking new items, goodwill gift, OOS substitution as make-good), `order_modification` (`edit_order`), `warehouse_hold` (`warehouse_hold`), `cancellation` (`cancel_order`), `customer_profile_update` (`update_customer`), `discount_code` (`create_discount_code`), `split_shipment` ([split_shipment](../../customer-service/lib/tools/splitShipment.js) — placeholder-fulfills held SKUs on the original order and creates a $0 pre-order containing them), `order_consolidation` (`consolidate_orders` — merges two unfulfilled orders into one shipment without cancel/refund), `invoice_kept_items` (`create_invoice_order` with `paid_items` only — covers customer kept exchange items + wants to pay, AND customer was refunded then changed mind and wants to be re-billed; the new invoice payment naturally reconciles any prior refund, no separate refund reversal needed). When `action_type` is null and `status` is `needs_info` / `route_to_human`, the draft is informational or pending customer input — no operator action prefilled. Don't introduce action_types that don't correspond to a write (e.g. the legacy `fulfillment_check` was a vague "look at this" flag with no tool — removed). When adding a new action_type it must (a) name the operator's user-visible intent, (b) have a matching MCP tool in [operatorTools.js](../../customer-service/lib/operatorTools.js), (c) be added to the whitelist in [aiAdvisor.js parseStructured](../../customer-service/lib/aiAdvisor.js), and (d) have a dashboard prefill in [app.js](../../customer-service/dashboard/public/app.js) that reads `operator_action_summary` directly when the payload doesn't decompose into structured fields. When two action_types share a tool, the dashboard's `actionTypeFromTool` takes `draft.action_type` as a hint to disambiguate (don't blindly override).
- **Operator agent confirmation handling: tool call mandatory, never re-preview.** On any operator yes/confirm/proceed signal (including the dashboard's "Yes, confirm" quick-reply), the operator agent's next action MUST be a tool call — the same tool from the most recent "awaiting confirmation" preview, with `confirmed: true` and the same arguments (draft_order_id / _refund_data / _fulfill_data / keep_order_number+drop_order_number / etc — whatever Phase 1 said to pass back). The agent does NOT re-show the preview, narrate, or ask "shall I proceed?". Earlier looser wording ("proceed with phase 2") let the model loop into Phase 1 again on hand-rolled multi-step flows; the strengthened positive directive lives in the operator system prompt and treats Phase-2-as-prose as a forbidden pattern.
- **Advisor-proposed warehouse holds execute at intake, not on operator command.** The advisor's hold template is past-tense ("I've put a hold on the order"), so the hold must be real before the draft is filed — otherwise the operator sees a draft that lies. [processGorgiasTickets.js autoExecuteAdvisorHold](../../customer-service/intake/processGorgiasTickets.js) calls `handleWarehouseHold` synchronously when `structured.action_type === 'warehouse_hold'` and seeds the draft's `actions[]` with a real `warehouse_hold` entry on success. On failure (in_progress / not found / API error) it omits the entry and the operator agent will attempt the hold itself when engaged. Two anti-patterns this replaced: (1) operator agent treating `draft.action_type === 'warehouse_hold'` as "hold is placed" — that's a proposal, not an execution; only entries in `draft.actions` count. The `holdAlreadyPlaced` check in [operatorAgent.js](../../customer-service/lib/operatorAgent.js) now looks at `draft.actions` only. (2) Dashboard's [apiActionChat](../../customer-service/dashboard/server.js) falling back to `draft.action_type` when an unrelated write completed — that let an `add_order_note` masquerade as a successful `warehouse_hold` in the timeline. Action entries are now filed under the actual tool name when no explicit mapping exists, never under the draft's intended type.
- **Refund/cancellation confirmations never state an exact dollar amount.** Both the customer-facing draft and the `operator_action_summary` omit the figure (the draft says "you'll get a confirmation email with the details"; the summary names the order + items). `refund_order`/`cancel_order` compute the real amount including shipping/tax, and Shopify emails the customer the exact figure. A hand-written advisor amount was the single most common operator divergence (draft "$32" vs actual "$28" when shipping isn't refunded). Exceptions: `invoice_kept_items` (prose total must match the invoice we set) and custom refunds that don't map to line items (DDP duties) still pass an explicit amount to the tool.
- **One-click "Execute & Send" runs the operator action and sends the draft in the background, gated on an AUTO_CONFIRM verdict.** Human stays the gate (operator reviews, then clicks); the button only collapses the execute → confirm-phase-2 → send dance. The operator agent emits `AUTO_CONFIRM: SAFE | HOLD — reason` on phase-1 previews (parsed into a structured field, stripped from the operator-facing text incl. during streaming). The dashboard auto-confirms phase 2 ONLY when the verdict is SAFE AND exactly one clean awaiting-confirmation write was previewed (mechanical backstop). Any HOLD/question/error/multi-write leaves the ticket untouched at phase 1 (nothing executed, nothing sent) and it returns to its tab flagged with a reason badge. Action runs before send; a phase-2 failure sends no email; a send failure after a completed action is a "half" state (action filed, draft still pending, retry send). Honors operator edits to both the draft email and the action box. Background = detached browser fetch with optimistic queue removal (simple v1: a toast doesn't survive a page reload, but server state stays correct). Ordering lives in the pure `orchestrateExecuteAndSend`; the gate decision in `evaluateExecuteSendGate` ([dashboard/server.js](../../customer-service/dashboard/server.js)).

- **Accuracy-eval ground truth: Jamie's sent reply, with two measurement caveats.** Compare the advisor's stored `draft_response` to the operator's `sent_response` over a stable-prompt window. (1) For ACTIONS, the ground truth is what the sent prose says Jamie did — NOT `cs_ai_drafts.actions[]`, which is incomplete (manual hold-releases/exchanges aren't all logged, so proposed-vs-`actions[]` over-counts errors). (2) Jamie's sent reply is strong evidence but not infallible — outlier cases can be his mistake; verify factual claims against the DB/catalog (the real source of truth), and don't encode a one-off wrong call as a rule.
- **Validate advisor prompt/tool changes with order-independent scenario tests, NOT live regen.** Re-running the advisor on historical tickets is confounded by order-state drift (China-window orders have since shipped/cancelled/refunded, so the advisor reads today's state and looks wrong). Use synthetic, order-free scenarios in [test/scenarios/](../../customer-service/test/scenarios/) (knowledgeFacts, deliveryGrounding, shippingPolicy, refundNoAmount, etc.); add a pinned scenario for every validated fix so it can't silently regress. The stored-draft baseline is faithful (generated in production); regen is not.
- **DB hard facts override KB/memory; the advisor looks them up.** Authoritative facts live in DB tables (shipping_zones = ship-to/rates/threshold/DDP; product_variants = colors/sizes/Tall/inventory/pre-order restock; order_delivery_times = transit). - **Delivered-but-not-received is handled directly, and the full ship-to address renders in advisor context.** When tracking shows delivered but the customer says it never arrived (stolen / porch pirate), the advisor states the tracking facts, confirms the full ship-to address back to the customer, suggests checking around (neighbours/household/front desk), offers a reship if it doesn't surface, and sets `needs_info` — it never tells the customer to file a carrier claim or escalates to human on first contact. `shipping_lookup` returns tracking facts only (called with `customerMessage: null`, so analyzer.js's regex "not received" copy never runs from the advisor path); the response is composed by the advisor prompt. Separately, the order-context block now renders the full street ship-to (address1/address2/zip), not just city/state/country, so the advisor can quote it for address-confirmation and address-change cases.
- **`pending_operator` / On Me tab — ticket state where Jamie owes the response.** Distinct from Snooze (waiting for customer, auto-follow-up armed) and Park (non-urgent deferral). - **Donation routing copy — use tool's response_text as-is, no state-conditional framing.** `get_donation_partner` returns a `response_text` with clean, neutral copy. The advisor must not add language like "we don't have a partner in [state]" — routing is by geographic proximity and an out-of-state partner is expected and doesn't need explaining.
- **Fulfilled-order notes surface in Waiting on Response.** Unresolved operator notes (`author != 'auto'`, `resolved = false`) for orders no longer in the Shopify unfulfilled set are included in the daily alert "Waiting on Response" section and in `list_pending_orders` via `fetchFulfilledOrphanNotes`.
