## What's Built

**AI Advisor (Opus-based):** AI reads full conversation + calls tools as needed. Handles exchanges, sizing, shipping, product questions, positive feedback. Structured output: the legacy `<structured>`-block-in-text shape is the production default (schema-enforced JSON via `advisorOutputSchema.js` shipped 2026-06-11 but was turned OFF by default 2026-06-13 — grammar requests are 3-20x slower and the first thing Anthropic load-sheds; opt back in with `ADVISOR_SCHEMA_OUTPUT=1`). The output parser is mode-aware and handles both shapes. All business rules live in the system prompt. Injects recent related exchange/refund/defect tickets via history_summary for second-round follow-up context. Resilience layers: malformed-output → route-to-human placeholder; 529 on large schema-enforced requests → automatic one-flip fallback to the legacy `<structured>` output mode per draft.

**Closeness-to-Final Judge (2026-06-10):** continuous quality yardstick — Opus judges every sent draft against what Jamie actually sent (categories: identical/cosmetic/substantive/factual_correction/action_divergence + a draft_may_be_right flag). Runs in the daily sync; digest headline = substantive-divergence rate (supersedes raw edit-rate). Verdicts in `cs_draft_judgments`. 90-day baseline: closing 97% clean, overall divergence improving over time.

**Auto-send (shadow phase, 2026-06-11):** gate (`autosendGate.js`) with a hardcoded never-list (money/orders/actions never eligible) + per-category `system_flags` allowlist that only Jamie promotes. Shadow mode marks would-have-sent drafts (`auto_close_path='autosend_shadow'`) — nothing sends. Dashboard: Auto-send allowlist panel + Closed-tab AUTO filter; digest dry-run line with judge-verified would-have-erred count. First watched category: closing.

**Steer & Send (shadow phase, 2026-07-23):** measures whether a steered regen could skip the final review glance (one-click steer→execute→send is the eventual tool). Gate (`steerSendGate.js`): deterministic checks (autosend never-list, any/changed `action_type` → ineligible, prose-only scope) then an Opus correctness verifier (steer implemented, claims grounded in context, no unrequested extras — fail-closed). Every dashboard steered regen records a `would_send` verdict to `steer_send_shadow` (flag `steersend_shadow`); nothing sends. Digest dry-run line cross-refs the closeness judge on gate-passed drafts (would-have-erred = go/no-go). Baseline going in: 32% of steered sends still diverge meaningfully (90d judge data), so live mode needs the post-verbosity-fix rate to collapse first.

**Training-signal capture (2026-06-10):** all three send paths log to `cs_ai_feedback_log` — sent/edited, `bypassed_*` (operator ignored a pending draft), `manual_*` (no draft) — plus `operator_steer` + `regen_count` columns. Historical backfill done.

**Tool Ecosystem (30+ MCP tools):** Lookup (customer, orders, products), actions (create/edit/refund orders, exchanges, wholesale orders, warehouse holds), analytics (LTV, margins, inventory, delivery estimates, reviews), knowledge (CS history search, FAQ, sizing guide).

**Dashboard (web-based):** Real-time Gorgias ticket queue with tabs (New, Follow-up, Parked, Snoozed, Closed) plus global ticket search across all statuses by customer name/email/order number/summary. Operators review AI-drafted responses and approve/edit. Operator agent for complex order manipulations. Ad Hoc Operator tab: context-free queries and actions against all CS tools (Opus, ephemeral history). Mobile-responsive PWA. Deployed on Railway at ops.rubyshines.com.

**Intake Pipeline:** Two pathways -- Gorgias ticket webhooks and Gmail CS parsing. Both feed through the AI advisor, store drafts in Supabase, and auto-assign handled tickets to "RUBIES AI" in Gorgias.

**Exchange System:** Two-phase flow. Phase 1: AI determines size, creates draft order in Shopify, shows preview with links. Phase 2: operator confirms, marks paid. Only uses FULFILLED non-cancelled orders for current size (ignores $0 exchange orders). Auto-finds correct order unless operator specifies one. Differing-items exchanges route through `exchange_difference` (read-only planning tool) — applies live volume/sale discounts to the new items per line (Shopify won't auto-apply automatic discounts to API draft orders), credits returns at actual-paid via Shopify's refund calc, and returns a recommended action: invoice (only if the operator explicitly asked to charge the difference) / auto-refund (net<0, no asking) / free exchange. Straight swaps skip it. The advisor reaches the same computation through `exchange_price_check`, a narrower read-only view returning a settlement verdict and no figures. See [exchangeMath.js](../../customer-service/lib/exchangeMath.js) + [tools/exchangeDifference.js](../../customer-service/lib/tools/exchangeDifference.js).

**Donation Routing:** After exchange, routes old items to LGBTQ+ partners. Geographic matching (Google Maps geocoding + haversine distance), load-balanced across 3 closest partners. Skips for defects. Full explanation of gender-affirming program in customer message.

**Knowledge Base (rebuilt 2026-07, corpus harvest):** 292 source-linked, trust-tagged articles (published site tier + founder-reviewed reply-corpus tier) with Voyage embeddings. Advisor searches it via the `search_knowledge` tool (kill switch: system_flag `advisor_kb_search`); weekly Monday refresh re-harvests the site, propagates amendments, and flags drifted sources for re-extraction (`customer-service/sync/refreshKb.js`). Pipeline + protocols in `customer-service/import/` (harvest, extraction, mining, triage, review sheets).

**Auto Follow-ups:** Two stages, fired by the daily sync's follow-up sweep (gorgiasAdvisorResync.js, 12:30 UTC cron) — Gorgias emits no webhook on snooze expiry, so the sweep is the real engine (a re-snooze set at ~12:35 by the sweep can miss the next day's ~12:31 pass by seconds; Stage 2 then lands a day late — known, accepted). A Haiku classifier first closes tickets that already look resolved. Stage 1: care@ via Gorgias ("just following up"), re-snoozes 3d, refreshes the dashboard conversation snapshot. Stage 2: personal jamie@ via SendGrid (quotes original response), records an internal note in Gorgias (the email itself exists only in Gmail), closes ticket, refreshes snapshot. Customer reply during snooze resets stage to 0; replies to Stage 2 stay in Gmail (intake skips them).

**Refresh on a templated outreach re-runs its own generator (2026-08-25).** The dashboard's Refresh sent every outbound draft to the general composer, so regenerating an A/B/C pre-order email produced a different kind of email entirely (raw SKUs and the shipping address quoted into customer copy) and dropped the case classification that decides what the customer is offered. Drafts now carry `structured_output.outreach_kind`, and Refresh routes back to the generator that produced them; a steer is treated as a deliberate handoff to the composer. Two things this bought beyond fidelity: an unsteered Refresh is the operator asking *"does this still hold?"*, which re-running detection answers directly, and when it no longer holds the draft body is REPLACED with the reason plus a ⚠️ flag rather than left looking sendable. That last part matters because a stale outreach reads exactly like a live one, so the operator's only signal would be remembering that the code changed underneath it.

**Unnotified Pre-Order Outreach (auto-drafter):** Detects unfulfilled orders containing a paid item at inventory ≤ 0 whose line item lacks the `Pre-order` customAttribute. Classifies each order A/B/C, composes per-case outreach with restock ETA from variant metafields, seeds a pending CS Advisor draft via `seedOutboundDraft()`. Each candidate verified against live Warehance `ready_to_ship` before flagging. Runs as a sweep on the always-on webhook server (every 10 min), not the daily cron. See [reports/lib/unnotifiedPreOrder.js](../../reports/lib/unnotifiedPreOrder.js).

**Pre-order lifecycle tools (2026-07-16):** the recurring slip-communication loop. `preorder_hygiene` reconciles all open unfulfilled orders against live Shopify + Warehance (mirror drift, refunded-but-open, ready-but-unshipped, stuck orders, line-attribute drift; fixes are opt-in flags) and lists the waiting population by promised text. `preorder_update_notice` sends a delay wave: operator passes the promised texts + new date phrase; two variants (pre-order-only gets a swap offer, mixed gets split-or-swap), plain email from care@ via SendGrid with no upfront ticket (replies create tickets via normal intake); every candidate verified `ready_to_ship === false` in Warehance; live sends logged to `preorder_notifications` for cross-wave dedupe. dry_run → test_send → send. CLIs: `scripts/preorderHygiene.js`, `scripts/preorderUpdateNotice.js`; logic in [preOrderLifecycle.js](../../customer-service/lib/merchandising/preOrderLifecycle.js); schema `customer-service/preorder-notifications-schema.sql`.

**Operator-knowledge loop (2026-07-09):** the fix for the sweep's #1 divergence driver (~37% = facts only Jamie knew). `advisor_facts` table → active facts injected verbatim into the advisor's static prompt (`buildFactsBlock`); the daily closeness judge proposes a `candidate_fact` on factual-correction verdicts (deduped against all statuses so rejected facts never requeue); dashboard Facts panel (approve-with-edit/reject/retire, manual add goes straight active, expiry dates auto-drop perishable facts). Logic in [advisorFacts.js](../../customer-service/lib/advisorFacts.js); schema `customer-service/drafter/advisor-facts-schema.sql`.

## Key Decisions

- **An order edit settles against what the customer PAID, and a SKU never identifies a line (2026-08-17):** three defects in `edit_order` compounded on one bundle order, each a case of trusting a figure that means something other than what it looks like. (1) **A SKU identifies a variant, not a line.** Bundle orders routinely carry the same variant on two lines at different prices (one bundle-priced, one full), so any "find the line" resolution keyed on SKU silently picks whichever came first; resolution takes a line ID, and an ambiguous SKU fails loudly rather than guessing. (2) **Shopify re-applies order-level discount CODES to lines added during an edit, but not manual/bundle line discounts.** A replacement line must therefore be priced against the PRE-code base — pricing it against the effective price the customer paid takes the code off twice. This is invisible in the Phase 1 preview because Shopify only applies the code allocation on commit, so a dry run cannot catch it and committed totals must be verified after. (3) **`totalPriceSet` GROWS to include lines added by an edit** (one swap pass took it from $403.92 to $747.26), so any delta measured against it is meaningless; `netPaymentSet` is the only figure that answers "is this customer up or down". The common thread: on an edited order the original totals stop being a record of the transaction, and a preview computed before commit cannot see what Shopify does at commit.
- **Pre-order wave truth is live Shopify + Warehance, never the mirror.** Line-item `Pre-order` attributes are null in the mirror for orders last synced before 2026-05-01, mirror open/closed state drifts (the order sync only pulls open orders, so a missed fulfillment webhook never self-heals), and Warehance `ready_to_ship === false` is the only valid "waiting" signal since Shopify inventory 0 can be stock reserved on that very order. A past-dated promise whose stock arrived (reserved) is declared via `stale_targets` — operator judgment. Run `preorder_hygiene` before every wave.
- **Agentic loops, not decision trees:** Opus controls flow. All exchange/sizing/response rules live in the advisor prompt, not in code. The old deterministic tree (`walkTree` + the `prescribe*()` phases in `sizingEngine.js`) was deleted 2026-08-24, ~1,900 lines, four months after it stopped being called. What `sizingEngine` still owns is the sizing *utilities* the advisor's tools sit on — nicknames, classification, size lists and adjacency, grading deltas, chart category, one-piece fit — and nothing that decides what to say.
- **Dead code that still looks alive is where a fix goes to be quietly discarded (2026-08-24).** The tree survived as "harmless, delete it later" from April and the bill came due in August: PR #143 implemented the arriving-soon sentence *inside* it, so the change shipped, the suite went green, and no customer could ever have seen it — the live gap stayed open until it was found by hand. It also forced the same customer sentence to exist twice, kept in sync by hand. The tell sat in the file header the whole time ("no longer in the active execution path... will be removed in a follow-up cleanup") and read as documentation rather than as a warning. What kept it alive was its own test suite: ~1,500 lines exercising live utilities *through* the dead API, so deleting the caller looked like deleting coverage. That is the shape to watch for — **when a deletion is blocked by its tests, the work is moving the assertions onto what is actually live, not keeping the caller.** Here that meant `analyzeOnepieceFit` (called by a customer-facing tool, previously covered by nothing but a `typeof === 'function'` check) gaining real behavioural tests against a stubbed size chart, plus a test asserting the deleted names can never come back.
- **A lookup narrower than the classifier it feeds silently deletes a branch, and the fallback answer is the one that lies (2026-08-24).** `analyzeOnepieceFit` classifies by distance — same size is `exact`, one away is `wiggle`, two or more is `separates` — but `lookupHeightVariant` only ever searched ±1, so `separates` could never be returned. Every such customer fell through to `height_outside_range`, whose message says her height is outside our charts. That was **false**, and false exactly where it hurts: the adult height bands barely move with size (XS-L Regular 62-66, S-L Tall 66-70, 1X-3X Regular 66-69 and Tall 69-73), so the mismatch lives at the ENDS of the range. A 2X customer at 63" was told her height was out of range when 63" sits squarely in the Regular band two sizes down. Measured across the whole waist-by-height grid: **24 of 90 combinations returned the false statement, all at the size extremes** — XXS, XS and 2X/3X/4X, the customers most likely to read "outside our range" as "they don't make anything for me". The fix searches the full size list nearest-first (one query for the chart, not one per size) and changed exactly those 24 cells, leaving every `exact` and `wiggle` answer untouched. Two things worth keeping: **an unreachable branch is a claim about the code that no test was making**, so the pinned tests now cover the boundary in both directions rather than only the happy path; and the handler had been *importing* `getSeparatesText` while paraphrasing it inline, so the customer sentence existed twice — the tool now returns the founder-written one as `customer_wording` and the paraphrase is gone.
- **A product's size range has ONE source: the catalog (2026-08-24).** `getSizeList` used to fall back to a generic run (`XXS…4X`, or the full youth numerics) per category, so it offered sizes a product is not made in — `getAdjacentSizes('XS','down')` on the Sky one-piece returned `['XXS+','XXS']`, neither of which has ever been a Sky variant. Same family as offering a style we cannot ship, one step earlier: the advisor can name a size that does not exist. It now reads `products.kid_sizes` / `adult_sizes` — the Shopify metafields synced by `syncProducts.js`, which is what `compare_products` already read — loaded into `PRODUCT_SIZES` by `initCsConfig` so the function stays synchronous and refreshes with the catalog (products webhook, daily sync, `reload_products`). **`product_cs_config.sizes_override` is retired and all rows cleared**; a hand-maintained range beside the catalog is the duplicate this removes, and it had already gone stale — the Naomi's said XS-2X while it is made in XS-4X, hiding two sizes from the customers who need them most. Measured over the catalog: 15 of 22 active products offered at least one phantom size before, 0 after. Details that carry the design: the youth and adult runs are stored **separately**, because concatenated they make youth 16 the size below adult XS and a step-down walks out of adult sizing; an empty run on a product that has the other one returns **null** rather than falling through, since "the Naomi has no youth sizes" is a fact and the fallback would have offered a youth Naomi; accessories return null outright, as a pin or an earring has no size axis and its SKU's last segment ("3", "S") parses as one; and the hardcoded `CHEST_PAD_SIZES = S/M/L` survives only as a fallback, since the catalog knows the plain pads are S/M and only the Magical pads have an L. Founder ruling settled along the way: adult XS/XS+ are youth 12/13 on the one-piece and XXS/XXS+ are youth 10/11 on the swim charts, which is what `NUMERIC_TO_LETTER_UPPER` already says — charts and code agree and neither needed changing.
- **The `sizingEngine` test fixture is generated from live data, never hand-written (2026-08-24).** Every hand-edited version drifted from production and either hid a bug or invented one: the missing generic `no-tuck` config row hid the keyword-ranking defect for 2000+ tests; hand-typed size ranges made the Sassy look like it had no XXS when it does, which produced a test asserting a false fact about a real product; and invented handles would have broken the `products` ↔ `product_cs_config` join the size range depends on (they are the same string in production, and the fixture had them differing). Regenerate it — config rows, handles, keywords, categories and the size metafields — rather than editing by hand. Regenerating it immediately failed four tests that had been encoding fixture-only products (a gift-card row that does not exist in production, chest pads as S/M/L when the plain pads are S/M).
- **One shared tool-loop engine:** every agentic loop (advisor main+shadow, operator main+shadow, ad-hoc standalone) runs on `customer-service/lib/runToolLoop.js`; callers inject divergent behavior via callbacks (dispatch, streaming, 529/stall fallback, abort, shadow allowlist). New agents use it — don't hand-roll the call→dispatch→append loop again. (Phase 4 of the 2026-07 review, shipped 2026-07-08.)
- **Structured output:** Advisor returns `_structured` JSON alongside customer-facing markdown. Dashboard consumes structured data directly.
- **Exchange sizing from SKU, not variant title:** Last segment of SKU is the canonical size.
- **Advisor prompt changes:** Always trace execution path, read audit trails, check existing rules before modifying. Don't add rules that duplicate existing logic.
- **Operator facts are injected, not retrieved.** Approved `advisor_facts` render inline in the static prompt rather than behind a search tool — the failure mode being fixed is the advisor not knowing a fact exists, so retrieval (which requires knowing to look) can't fix it. Growth valves: Jamie's approval gate, expiry on perishable facts, dedupe-on-propose, and a retrieval fallback only if the set ever exceeds ~200 facts. Facts state durable business truths; live data (inventory, order state, rates) stays tool-fetched and wins on conflict.
- **A wrong operator fact cannot be fixed with a prompt rule — check `advisor_facts` before writing one.** Facts outrank KB search by design (precedence above), so an advisor holding an inaccurate fact answers confidently and never searches. Measured 2026-08-05: a fact asserting the foam chest pad set "comes in sets of three" produced wrong product comparisons at 0/3 against two different placements of a new grounding rule, and went right as soon as the fact was corrected. The corollary is a three-layer sweep whenever the advisor states something wrong and confident about a durable fact: correct the fact, re-extract the KB candidate (`loadKbCandidates.js` + `rebuildKnowledgeBase.js` — the weekly refresh re-harvests `kb_sources` but only FLAGS drifted candidates, it never re-extracts them), and fix the source-of-truth copy on the site, or the next harvest reintroduces the contradiction. Facts also have to be SYMMETRIC across products the advisor will compare: giving one product a precise structure and its sibling none leaves a gap the model fills by inventing a contrast, and a fact forbidding the invented phrasing measured identical to no fact at all (2/6 either way). The fix is a parallel positive fact on the sibling, which took the same case to 0/6.
- **A fact earns its place only when no system of record could hold it (2026-08-11).** `advisor_facts` was built to patch operator-only knowledge but drifted into a general knowledge base, because the closeness judge mints one fact per correction: the list is a log of past mistakes, so its coverage is whatever customers happened to ask about and whatever Jamie happened to correct. That produces the asymmetry the entry above warns about, at scale. An audit retired 42 of the 58 facts then live. Largest group by far was product comparisons the catalog, the tech packs, or the KB already answer — and two of those were wrong in a way the data was not (a "Ruby has 2 inches more waist than the Cheeky" the specs put at ~0.9in; a "unicorn print is youth only" the catalog contradicts). Then size-chart arithmetic restated four times, then four near-copies of the donation policy, then a pending fact naming one partner org as *the* return address, which would have misrouted every customer living elsewhere. The gate is now the one the KB always had — look-up-able facts live in their systems of record — and the judge prompt applies it when proposing, so the list stops refilling. What legitimately remains is founder knowledge with nowhere else to live: why we make no white bottoms, why there are no new colourways, what to do when a DDP country charges duties anyway. **The nulled proposals are not discarded — they are the tool backlog.** When the judge declines to propose a fact because a system owns the truth, it instead names the tool that should have answered (`cs_draft_judgments.tool_gap`), and the daily digest lists them, so a correction becomes a data fix rather than prose. That inverts the loop the facts table created: the old one absorbed every tool gap as a sentence and hid it.
- **Product-cut comparisons live on `product_cs_config.style_switch`, surfaced by `compare_products` (2026-08-11).** The advisor guessed at cut differences because `compare_products` returned only Shopify PDP blurbs ("Full coverage" vs "Cheeky cut, lower rise") — not comparable, so the model invented a contrast and each correction became another prose fact. The `style_switch` field already existed for exactly this and nothing surfaced it: read in one place (`sizingEngine`'s style-switch branch), and even there the computed value was dead code sitting beside a hardcoded product list. It now returns per-alternative plus as a category-level `style_switch_options` list. Because a half-filled comparison set is worse than an empty one, all four higher-leg styles are marked (Sassy, Naomi, Flo, Cheeky), not the two that were. Deliberately NOT built: a measured version reading leg opening and rise from `tech_pack_specs`. Specs are the right instrument for *verifying* a claim during an audit and the wrong one at runtime — they are flat tech-pack numbers a customer must never be quoted, the Naomi has no leg-opening POM at all, and a second comparison mechanism beside `style_switch` rebuilds the two-corpora contradiction behind the 07-22 sorry drift.
- **`style_switch` carries two meanings and they must not be collapsed: `isTarget` is the cut fact, `recommendFor` is the suggestion (2026-08-11).** Making `sizingEngine` read the same field `compare_products` reads looked like pure cleanup and was not: asking the config for `underwear_bottom` targets returns Flo, Naomi and Sassy, and offering all three would have regressed the recommendation. Two things the cut fact cannot express — the Flo is youth-only (which lived in the note *text*, where no code could read it) and the Naomi is a gaff, cut higher but buying compression at some cost to all-day comfort. Hence `recommendFor: { tightLegs, ageGroups, everyday }`: a style can be a wider cut without being what we suggest, and the everyday flag orders the copy. **Founder ruling on how to say it: name the all-day pick, never state the trade-off outright** — "the Sassy is the one most people find best for all day wear", not "the Naomi is less comfortable" — with a test asserting the copy carries no compression/comfort language. Two deliberate behaviour changes came with it: a customer already on the Sassy is now offered the Naomi rather than dead-ending at "already the widest, size up" (which contradicted the rule that a correct waist should not be sized up to fix the legs), and a one-piece no longer falls through to being recommended an underwear style. Generalises: when one field feeds both an advisor-facing lookup and a customer-facing recommendation, the recommendation needs its own scoping, because the lookup's truth conditions are weaker.
- **The tight-legs recommendation checks stock, and product matching ranks by specificity not keyword length (2026-08-13).** Two fixes that both come from the same place: the deterministic prescription and the advisor tool were answering the same question from different data. `prescribeSizingResolution` stays synchronous and pure, so availability is resolved at the async boundary in `walkTree` and passed IN (`{ availability }`); omit it and behaviour is unchanged, which is what keeps every existing caller and test valid. A style is offerable when in stock, or out of stock with a restock inside the offer window, so the reply stopped promising the Naomi (zero in every size, no inbound). Two traps worth not rediscovering: `searchProducts` is fuzzy and returns OTHER products, so a search for "Naomi M" surfaced the Ava's 168 units and made an out-of-stock style look stocked until the filter matched on product title as well as size; and product-keyword matching ranked by keyword LENGTH, which is backwards, because the generic legacy row's `no-tuck` (7 chars) outranks `ruby` (4) and appears in most product titles. Specificity (how many titles and handles a keyword matches, fewest wins) is the correct rule, counted over titles AND handles so it still works when the product table is not loaded. The fixture had never contained the generic row, which is why 2000+ tests never caught it: adding it broke 24 tests immediately and that failure was the reproduction.
- **Tight legs with a fitting waist: lead with the roomier opening, give "cut higher" as the reason (2026-08-13).** Founder wording, and the order is the point. "Higher leg cut" on its own reads to a customer as *more revealing* rather than *roomier*, which is the opposite of the reassurance someone with fuller thighs is asking for. Tied to the opening it reads as the fit benefit: *"The [product] has a roomier leg opening as it is cut higher, so there should be more room for the thighs."* (Consequence clause revised 2026-08-23, replacing "so the thighs get more room without sizing up the waist" — the waist tie is not lost, because the reply already states it as its own sentence and DO NOT SIZE DOWN is a separate instruction.) That sentence is a verbatim template in the advisor prompt (positive templates stick, descriptions drift), and the same vocabulary is used in the product-knowledge lines, the `compare_products` tool description and the `style_switch` notes, so the model is never choosing between two ways of saying one fact. A test asserts the roomier opening precedes the reason and that the reply never leads with "higher leg cut".
- **Supply has three states and the middle one has to carry its own name (2026-08-23).** In stock now / arriving soon enough to be worth waiting for / not available. The arriving state shipped as data only: `worth_offering: true` nested inside a key called `style_switch_unavailable`, with nothing in the prompt naming the field. The model collapsed it into a neighbour — dropped the style, or named it in the in-stock register, which was the only template it had. Same class as "guidance that lives only in the JSON schema has never shipped": the decision was written in code, so it never reached the model. Now an arriving style sits in `style_switch_options` beside the in-stock ones carrying `availability` and `back_in_stock`, with a verbatim prompt template and an explicit list of the internal fields (eta, sellable_estimate, transfer_number …) that never reach a customer. **Ordering is a founder ruling: fit leads, an arriving style is not demoted for arriving** — at one to two weeks out we offer it first, and stock only breaks a tie between equally-positioned styles, or the better-fitting option silently loses to a worse one that happens to be on the shelf. And it is framed as an exchange we hold, never a purchase or pre-order: the customer already owns something that does not work.
