## What's Built

**Prospect Discovery Pipeline:** Google Maps searches across tier-1/tier-2 cities with targeted search terms (LGBTQ friendly boutique, swimwear shop, etc.). Deduplicates by Google Place ID and website domain.

**Scraping Pipeline:** Puppeteer scrapes homepage + key pages (about, shop, contact) for each prospect with a website. Browser instance recycled every 10 pages for memory management. Rate limiting: 1s between domains, 2s same-domain subpages.

**Contact Finder:** Regex + DOM parsing extracts email, phone, contact form URL. Classifies email type (business/personal) for scoring.

**AI Analysis:** Claude analyzes scraped HTML. Returns structured JSON: subcategory (bra-fitting, online-trans-retail, etc.), trans/gender-affirming mentions, product type, ownership (independent vs chain), presence, brand list, outreach angle.

**Lead Scoring:** Points-based 1-10 scale. Positive: trans mention (+3), LGBTQ/inclusivity (+2), carries gender products (+2), underwear/swimwear (+1), independent (+1), physical store (+1). Negative: chain (-2), no website (-2). Threshold: score >= 5 = qualified.

**Google Sheets Sync:** Exports qualified prospects for sales outreach.

**Wholesale Orders (MCP tool):** Two-phase confirmation like exchanges. Pricing defaults: US/AU 50% off, others 30% off, free shipping, AU auto-splits at $1k AUD. Negotiated per-partner terms (discount %, incoterms DDP/DDU, forced currency) live on `b2b_companies.wholesale_*`, matched by customer email (`lib/wholesaleTerms.js`); precedence is explicit param > stored terms > country/zone default. Stored terms as of 2026-09-03: Transting 50% + DDU, Sock Drawer Heroes USD, Tuck and Bind USD (replaces the old hardcoded currency override).

**Store Locator (MCP tools):** `store_locator_*` tools (list/create/update/delete/publish) manage the rubyshines.com/pages/store-locator map. Data lives in `b2b_companies` (9 new `locator_*` columns + `on_store_locator` flag). Publish writes `rubies-ecom-v4/assets/store-locators.json` via worktree + auto-merge, same pattern as donation partners. Haiku auto-extracts store descriptions from the website. 7 retail partners live as of 2026-06-08.

**Outreach Engine (2026-06-11):** the unified B2B outreach system (design record + unbuilt-remainder spec: `.claude/plans/b2b-outreach-system.md` — code is truth for what's built). One spine, three channels (retailers / LGBTQ+ orgs / affiliates): 6-tier signal-based queue, cadence engine (per-message-type due conditions), two Opus advisors (`b2b_sales_advisor`, `b2b_community_advisor`) drafting into `b2b_drafts` with enforced output schema (facts_to_verify + open_commitments fields instead of "don't hallucinate" rules), Gmail reply correlation (inbound → company thread, bounce/departure detection pauses cadence), and a two-phase send tool **hard-gated by the `b2b_send_enabled` system flag (default OFF — go-live is a Jamie-only act)**. Surfaces: operator-console tools (`b2b_queue`, `b2b_draft`, `send_b2b_email`) + dashboard Outreach panel. Tables: `b2b_threads`/`b2b_messages`/`b2b_drafts` + outreach columns on `b2b_companies`. Engine outbound `b2b_messages` rows are written by the send tool; manual Gmail sends are reconciled in as `source='manual_send'` (see below).

**Panel truth layer (2026-07-24):** the queue and history are kept honest against Gmail. `manualSendReconcile.js` backfills messages the engine didn't send — Jamie's manual Gmail replies (`manual_send`) and pre-correlation inbound (`gmail_backfill`) — idempotent on `gmail_message_id`, DRAFT-labeled messages skipped (the checkpoint-poison guard), 15-min per-thread cooldown, runs on queue/history fetch. Reply-rate/A-B metrics still count only `source='send_tool'` rows. Closed threads never produce Tier-1 "waiting on us". Dashboard panel shows full conversation history per company (`GET /api/b2b/companies/:id/threads`). `syncB2bCompanyState.js` (daily-sync-all sub-pipeline, after Orders) keeps `b2b_companies` order fields, `relationship_state` promotions, and org `program_flags` true from the orders mirror + donation_partners registry — cadence never nudges from stale order data.

**Relationship summary (2026-08-13):** `b2b-outreach/lib/relationshipSummary.js` keeps a per-company rolling recap + suggested next step on `b2b_companies` (`relationship_*` columns), rebuilt from `b2b_messages` — incremental when messages only append, full rebuild when any land behind the watermark. Sweeps nightly in `daily-sync-all`; `POST /api/b2b/companies/:id/summary/refresh` backs the panel's ↻. Surfaced in both the panel and the `b2b_search` console tool, and in the advisor's context. Restores what the pre-migration Google Sheet carried per company. The Outreach detail pane is restructured around it: a "Where this stands" block (stat strip, recap, next step, cadence reason) above the composer, conversation beneath as the audit trail, shaped like Gmail — the live thread open with its newest message expanded and earlier ones as clickable stubs, concluded threads shut.

**Thread discovery sweep (2026-08-19):** `sweepEmptyCompanies` in `manualSendReconcile.js` searches Gmail nightly for companies holding zero `b2b_messages`, across every address on file. Runs in `daily-sync-all` immediately before Relationship Summaries, so anything imported is summarised the same night. Bounded per run, ordered so companies claiming a relationship they cannot evidence go before untouched prospects, and stamped with `threads_discovered_at` so companies with genuinely no history back off.

**Browse surfaces (2026-07-29):** the Outreach panel answers three questions, one sidebar mode each — **Queue** (what's due, the original 6-tier view), **Activity** (`GET /api/b2b/activity`, every message newest-first across all companies), **Companies** (`GET /api/b2b/companies`, searchable directory of all of them, filtered on two independent axes: relationship stage and conversation state). Search spans company name/slug/domain/general email, contact email + name, and thread subject, and returns *which* matched. Closed threads carry Reopen (flips status open + drafts the follow-up threaded on that conversation) and its mirror, Close. Same `queueService.js` functions back the panel and the `b2b_search` / `b2b_activity` / `b2b_reopen_thread` console tools.

**Meeting scheduling (2026-08-20):** a Schedule control in the Outreach panel reads Jamie's three calendars and either shows availability (read-only) or books the call — creating `RUBIES x <Company>` with a Meet link, inviting the contact, and sending the reply in one action. Agent-agnostic tools (`calendar_availability`, `read_proposed_times`, `schedule_meeting`); calendar auth is a SEPARATE OAuth token from Gmail's, since re-minting that one risks losing `gmail.modify` and breaking CS intake. Meetings live in `b2b_meetings`; a booked call suppresses the cadence. Rehearsal mirrors `test_send`: real event, real invite, to Jamie only, writing nothing.

**Post-call follow-up + composer templates (2026-09-03):** the day after a booked call ends with no outbound since, the company surfaces at Tier 1 (`post_call_followup`, deliberately NOT an initiating type — no AI draft, ever) until anything at all goes out to them (manual Gmail sends included) or the operator dismisses it onto the meeting row; the moment expires after 30 days. The composer's empty state offers operator templates (`b2b-outreach/lib/messageTemplates.js`): `setup_call` (call ask, program summary included only when we never sent an intro; times always theirs to suggest) and `partner_onboarding` (orgs only — agreement spec + onboarding survey link + call-notes placeholder). Applied templates land in the pending compose row (`advisor: null`) with `template_id`/`template_body` in `structured`. Console tools: `b2b_template`, `b2b_dismiss_post_call`. Design record: `.claude/plans/b2b-post-call-followup-templates.md`.

**Bounce recovery (2026-08-20):** `b2b-outreach/lib/bounceRecovery.js` turns a hard bounce into queue work — parses the DSN, marks the outbound `b2b_messages` row `undelivered_at`, retires the dead contact (`bounced_at`), revives the approved text as a new pending draft at Tier 1 linked by `bounced_from_draft_id`, and clears the cadence date the failed send bought. Alternates (active contacts, then same-domain addresses seen in our own history, then the general inbox) are offered in the queue reason and never used automatically. `replayBounces.js` re-reads stored `email_messages` as the catch-up the fire-and-forget push path never had, running nightly in `daily-sync-all` before Thread Discovery.

**Inbound triage (2026-09-02):** the "New inbound" strip closes the cold-inbound gap — `correlateInbound` can only attach mail to companies that already exist, so a new org writing in was classified and labeled by the Gmail intake but invisible to the engine (Blue Mountain Clinic wrote twice before anyone noticed). `b2b-outreach/lib/inboundTriage.js` lists org/retailer-classified inbound matching no company, one row per identifying sender domain (free-mail senders excluded — an individual identifies no organisation); a Haiku pass extracts the real org name + country from the message (operator-reviewed in the strip's editable name field, so a miss costs an edit, never a wrong record). Admission-gated like Tier-4, never auto-created: **Add** creates the company (`source: inbound_email`, warm, vetted) + contact, imports their Gmail thread so they surface at Tier 1 "waiting on us" with no cold intro draft; **Ignore** records a lost stub row keyed on the domain (same motion as donation_partner_mark_out). Surfaces: strip atop the panel queue, `b2b_inbound` console tool.

## Key Decisions

- **Initiating messages are machine-drafted; continuations are operator-written (2026-09-02):** the advisor drafts only messages WE originate — org intro, community check-in, re-approach, reorder nudge (`INITIATING_TYPES` in cadence.js) — and does so automatically: a nightly daily-sync pass drafts every due initiating entry, so the queue is review work rather than click-to-generate work. Tier-1 replies and directory revivals get no AI draft (composer only): reply drafts kept asserting facts outside the record ("Wednesday is great" about a calendar the model cannot see), and line-by-line distrust of a draft costs more than writing the reply — the same reasoning that earlier removed advisor-proposed meeting times, generalized to all continuations. Initiating drafts run on Sonnet deliberately: locked template bodies, fixed system-assigned A/B subjects enforced by code override (the model never composes an intro subject — the A/B read requires byte-identical strings), tool-less advisor, operator review before send. The unreviewed follow-up ladder and anything reply-shaped stays Opus, and the stored ai-body-vs-sent-body edit rate is the flip-back tripwire. A genuine inbound reply auto-dismisses any waiting unscheduled initiating draft — the conversation is now live, which moves it to the operator's side of the line (auto-replies, calendar notices, and bounces do not).

- **A held call is a queue signal, not a draft, and templates fill only what a lookup can answer (2026-09-03):** the post-call follow-up is the strongest case of initiate-vs-continue — the facts that matter happened on a call no model attended — so the entry opens the composer rather than generating text, and a template types the boilerplate around the operator's own two lines. Every template fill is deterministic (first name via the same resolution the send uses, org name, country discount, meeting weekday in THEIR timezone, survey link), zero model calls; bodies are Jamie's real sent mail, not an invented register. Two guards make it safe: the call-notes placeholder is refused by `sendB2bEmail` with no bypass (the fix is always to write the two lines), and dismissal writes `followup_dismissed` on the meeting row scoped to PAST meetings only, because a dismissed future meeting would also stop suppressing the cadence. The filled original is kept in `structured.template_body` so operator edits to a template are the same measurable signal as edits to an advisor draft — the tripwire for whether a template's wording has drifted from what actually gets sent.

- **An absent or unverified fact is not neutral — something downstream fills it (2026-08-28):** seven distinct bugs this session were one shape. Klaviyo profile geolocation was stored as org location, so 130 orgs carried the datacenter that served their profile (Tampa filed as Des Moines, Chicago as Boydton VA) and the apparent Iowa/Virginia clusters were server racks. A street line geocoded without the state the analyzer had already derived returned a real address 900 miles away. A shipping list ("based in Germany; ships to Finland, Italy, USA") geocoded to Finland, MINNESOTA. An unfilled template placeholder outranked a working `info@` because its local part reads as *personal*, which `pickBestEmail` prefers. `program_flags` was read as "in a RUBIES programme" by two callers while enrichment wrote observations into it. `prospect` was set by a one-off repair and never re-derived, so the nightly Gmail sweep kept falsifying it and eleven vetted rows queued cold intros to orgs we already knew. And a donation-partner match that failed left the advisor with *silence*, which it filled by offering to start a programme that had already delivered 23 items. The through-line: we kept assuming a gap would be treated as a gap. It never is — a null becomes "never contacted", a missing region becomes whatever Google guesses, an empty facts block becomes "not a partner". **So say which kind of nothing it is.** Enrichment distinguishes `no_address` from `scrape_thin`; the advisor is told "they ARE a partner, records did not load" rather than being told nothing; a geocode outside the stated country or region is refused as `conflict` rather than written. Corollary on matchers: two matchers over the same question WILL disagree (the programme flag matches on domain-or-name, the routing lookup domain-only), and the strict one returning nothing is indistinguishable from "no relationship" unless it says so.

- **The cadence owns when a company is next contacted, not the operator (2026-08-27):** partner check-ins were three seasonal windows (Pride, back-to-school, year-end) against a 180-day threshold, which is twice a year on a rolling per-org date. Two of those windows were badly chosen — Pride is when these orgs are least able to reply, summer is when student-run ones are empty — and a rolling date scatters twenty check-ins at one every few weeks, which is the shape of work that never gets done. Now one October sitting at a flat 300-day threshold (under a year deliberately, so the window cannot be missed by days and slip another one). Snooze is deprecated in the same motion and for the same reason: every real use meant "do not start something yet", which is the cadence's own job, so it asked the operator to invent a date for a question the system could already answer. Its READING path survives — pause shares `deferredSince` and a stray value must keep behaving — but nothing new can be set. What the operator was actually missing was not a control but a **display**: the next-contact date is stored and shown nowhere, so the only way to be sure the system would not act was to stop it. Pause stays for the case no schedule can express ("not working Canadian retailers this year"). Reaching for a per-company override often means the interval itself is wrong.

- **A scheduled send is machine work and must not render as operator work, but hiding it cannot hide it failing (2026-08-27):** `mergePendingDraftEntries` puts any company holding a pending draft into the queue without consulting the cadence — correct for a draft awaiting review, wrong for one the automatic ladder has already scheduled. That one goes on its own, in the recipient's mid-morning, behind guards that all run at send time, so surfacing it asks for a decision already taken and undoes what the automatic ladder exists to do. Scheduled drafts are therefore excluded. What makes the exclusion safe is its expiry: a scheduled draft still pending `SCHEDULED_STALE_HOURS` past its slot comes BACK, badged stuck rather than presented as fresh work. Without that, this change would have permanently concealed the outage that prompted it — a fail-closed guard holding three follow-ups on every 15-minute tick, where the panel was the only surface the stall showed on at all. Fourth entry in this file about this one function, and the general form is the same each time: **any rule that removes rows from an operator queue needs a condition under which they come back**, or it converts a visible backlog into an invisible one.

- **The follow-up ladder anchors on the last chaseable outbound, and "have they answered?" is a question about THAT message (2026-08-26):** `answered` was `!!ctx.lastInboundAt` — any inbound ever — so the ladder could never fire for a company we had ever corresponded with. P10 Qc last wrote in 2022 and RISE @ LA in 2025; both were sent a check-in in August 2026 and both were permanently ineligible for a chase on the strength of those old replies. Nothing failed loudly: the queue showed nothing, which reads as "nothing due". The all-time rule existed to stop one real case (an org declines, we send a graceful close, our close is newer than their reply, so a timestamp comparison re-arms the chase), and the fix is to handle that where it belongs — `reply_close` is not a chaseable anchor — which lets the comparison be a comparison again. The anchor also moved off "the first-touch type ever in `sentTypes`", which only ever chased an intro and left `community_checkin`, `reorder_nudge` and the rest with no chase at all. **Generalises past this bug: a predicate answering a question about one message must be scoped to that message, and a flag summarising all of history will silently answer a different question.** Building it surfaced the same shape twice more — a company mid-ladder has no first-touch type in `sentTypes`, so the first-touch branch fired a cold intro underneath its own sequence; and the pass's report counted only what reached the queue, so companies genuinely overdue but held by the eligibility gate were absent rather than reported. Both are the absent-record-vs-empty-record rule again. Scope is deliberately narrow and enforced in the cadence rather than at the caller: engine sends only (`source='send_tool'`), inside 90 days. A manual Gmail send carries `message_type` null, so chasing one means guessing whether it was an intro or a goodbye — 51 of 60 unanswered threads are that shape, some 1575 days old.

- **A cadence-set On Me claim carries a note; an operator-set one still does not (2026-08-26):** the ladder ends by retiring a lead or, for an `active` relationship, handing it to Jamie — a partner we ship boxes to that ignored a check-in and two chases is not a dead lead, and has to be visible now rather than next season. On Me is the right vehicle rather than a new list (it already carries the ageing, the tab count and the digest section), and the engine going quiet on a claimed company is its designed behaviour, correct here because the last thing an unresponsive partner needs is a fourth automated email. The decision that removed the note is not reversed: its reasoning was the cost of **asking a human to type one** in front of a one-click decision, which does not apply to a machine that already knows why. The note holds only durable facts (a count and a date) so it cannot decay the way a hand-typed intent does, while what to DO still comes from `relationship_next_step`. `on_me_source` / `outreach_paused_source` keep the two kinds distinguishable — without them a resume leaving `on_me_source='cadence'` behind would make the next operator claim render as an engine hand-off, the same class of bug as the resume that once nulled only the pause columns. Retiring stays a cadence-set `outreach_paused_at`, never `relationship_state='lost'`, which would claim they said no.

- **Unattended sending is guarded on targeting, not on prose (2026-08-26):** a follow-up body is low-variance — the advisor holds the thread and the recap, and "circling back" is hard to get wrong — so the review a human would perform is not what makes it safe. What goes wrong is who it reaches, and every guard is therefore machine-checkable and runs immediately BEFORE the send rather than at draft time: a forced Gmail re-check for a reply that landed since, an address-health check, and a daily cap. The re-check is load-bearing because this engine has repeatedly turned out not to see its own correspondence, and it has to inspect the RETURN VALUE: `discoverCompanyThreads` and `reconcileThreads` are fail-soft by design for their other callers, so a try/catch alone passes cleanly in exactly the case that matters (Gmail unreachable) and would send blind. One of them returned a bare `{discovered: 0}` on a failed list call, indistinguishable from "looked, found nothing", and now marks it. **Scheduling into the recipient's mid-morning is what makes a click unnecessary rather than what replaces it:** hours pass between drafting and sending, so the review window exists for free. Where the timezone is unknown we do not guess one — we pick a time that is business hours in every zone the country spans (noon Eastern is 9am Pacific), which keeps the no-match-means-no-facts rule while still answering. That rule is deliberately looser than `meetingTimezone`'s: a wrong zone there lands verbatim in customer-facing text, whereas here the worst case is an email arriving early.

- **An attachment's identity is per-FILE for uploads and per-KIND for generated documents, and `structured` is operator state a compose silently discards (2026-08-26):** the draft table modelled attachments as specs keyed on `kind`, which is right for the partnership agreement — we hold the recipe rather than the bytes, render it fresh at send so it can never carry a stale org name, and a second agreement is the same agreement. Operator uploads break that assumption in both halves: we cannot regenerate them, and they are naturally plural (the lookbook AND the pricelist is one email), so keying them on `kind` would have made each new file replace the last with nothing on screen to say so. Identity is therefore `upload:<storage path>`, the path being unique per upload, and removal names a key rather than a kind. Bytes go to storage at ATTACH time, not send time, on the same reasoning as the composer's autosave — a refresh or a failed send must not lose work already done — and a spec whose object has since gone throws at send rather than letting an email that says "I have attached" go out with nothing on it. The second, more general half surfaced building it: **`b2b_drafts.structured` is where every piece of operator state lives** (attachments, `to`/`cc` overrides, `facts_verified`, `next_touch_days`), and `composeDraft` supersedes the pending row and inserts a fresh one with `structured: {}`. The empty-state Send composed at send time, so anything accumulated on the autosaved row was discarded at the last possible moment — invisibly, because the send succeeded. Any path that composes rather than updates has this bug; the empty state now saves into the same row it has been autosaving into. Size is checked against the TOTAL at send, not per file, because Gmail's 25 MB ceiling applies to the encoded message: two files that each pass a per-file cap still cannot go together, and the refusal has to name the numbers rather than surface Google's opaque error after the click.

- **Second instance the next day, Book & Send (2026-08-26):** the decision above predicted this bug and named the wrong predicate. It is not "composes rather than updates" but **sends without consuming the draft row** — `scheduleMeeting` composed nothing, it handed the composer's text to `sendB2bEmail` as a loose body, so a reader grepping for `composeDraft` callers would have missed it entirely. The row stayed `pending`, which is all `mergePendingDraftEntries` needs to put the company back in the queue at the tier frozen on the draft, without consulting the cadence: a booked, answered call read as outstanding work, and the only evidence of the defect was a queue entry for work that was already finished. Everything else on the row went with it — a booked reply sent with no attachments (including an agreement the operator had attached, under a body saying so), no To/Cc override, no `next_touch_days`, and no `sent_body`, so booked replies contributed nothing to the edit-rate signal either. Every send goes through `sendDraftById`; a second send path is how the row's state gets left behind. The corollary found while fixing it: the draft must be read BEFORE the recipient is resolved, because a To override lives on it and the calendar invite has to name whoever the email names — resolving them separately is how you book a call with one person and tell a different one about it.

- **Mail from a person is not always a person writing, and "we are done here" is a thread close rather than a deferral (2026-08-24):** a Google Calendar RSVP is sent FROM the contact's own address, so every layer treated it as a reply — and it necessarily lands AFTER our outbound invite, which is exactly the Tier-1 condition. Booking a call therefore put the org straight back in the queue as "replied, waiting on us" at the moment the scheduling was finished and there was least to say, and the only way to clear it was to hand-close the notification. The auto-responder exclusion already existed for this class; calendar mail simply was not in it. Inbound classification is now one function with a shared set of non-reply types, so the next member of the family lands in one place. Detection is precision-first in a specific shape: an RSVP subject decides alone (nothing else generates `Accepted: <thing>`, and it is the case that arrives with an EMPTY body over Pub/Sub, so it cannot be asked to corroborate itself), while `Invitation:` — a subject an org could plausibly write by hand — must be agreed with by the body or a `text/calendar` part. No `Re:` tolerance anywhere: Gmail threads on subject, so a human answering inside the notification's own thread is the false positive that would silence a real reply. The second half is the UI question this exposed: closing a thread was already the right answer for a correspondence that has simply ended, but the control sat under each thread in the transcript, repeated per thread, so acting on it meant first working out which of eight to close and closing the wrong one did nothing visible. The queue entry already knows which thread it means, so the relationship block acts on it directly — a bare button in the SAME row as the deferrals, with its explanation in a tooltip like "On me" next to it. Naming the thread in body text answers a question that only arises when several are live, restating how a control works on every render is chrome around a one-click action, and giving the odd one out its own row spent block space on a distinction that governs behaviour rather than layout. It stands alone only when a deferral banner has replaced that row, which a reply landing on top of a deferral can produce. **It is deliberately NOT a fourth deferral** — pause and snooze also stop the cadence, and "nothing more to say until the next check-in" is precisely the case where the next check-in must still happen.

- **A claim about an action must be backed by the action (2026-08-20):** clicking a slot writes "I just created an invite for…" into the draft immediately, because seeing the sentence is how you check the time is right — but only Book & Send creates the event, and the ordinary Send sat right beside it. A partner was told about an invite that did not exist, and nothing anywhere noticed: the email was well-formed, the send succeeded, the draft looked correct, and the only evidence of the defect was an absence. **The generalisable trap is a UI that writes a promise into text before the thing it promises exists, with a second control that will happily send it.** Disabling the superseded button is the obvious half; the load-bearing half is the check in `sendB2bEmail`, because it also covers the console, the MCP tool, and a draft sent after a page refresh — where the panel has forgotten a slot was ever picked, which is precisely when the operator has forgotten too. It fails OPEN on a lookup error, since blocking real mail over a database blip is worse than the thing it guards, and it needs an `invite_created` bypass because `scheduleMeeting` writes its own `b2b_meetings` row AFTER sending, so on the legitimate path the row cannot be the evidence. Repairing this case also revealed a missing operation: `skip_reply` books the event and sends no email, for when they have already been told the time and a second message restating it would be worse than silence.

- **A delivery failure is work, not silence (2026-08-20):** the bounce detector was correct and had never run once. Its only call site sat under `if (m.is_sent || m.is_auto_reply) continue`, and the Gmail intake marks mailer-daemon DSNs as auto-replies — so a bounce was precisely the message shape that could never reach the bounce detector. Two partner addresses died in the 19 Aug check-in round (2 of 17, **12%**, against the ~2% that burns sender reputation) with the sends recorded as delivered and nothing anywhere saying otherwise. **The interesting half is that detection alone would have made it worse:** `contact_unknown` makes `companyEligible` false and renders nowhere, so a working detector would have silently muted a partner — the engine going quiet about an org exactly when it learned something urgent. So the dead ADDRESS is retired and `resolveRecipient` falls through on its own, `contact_unknown` is reserved for when nothing is reachable, and the queue surfaces that case ABOVE the eligibility gate, because the gate is what hides it. Recovery is a **revival, not a regeneration**: `sent_body` holds the text the operator actually approved (on both real cases his rewrite, not the AI's draft), so it returns as a NEW pending row seeded from it while the original stays `sent` — its `sent_at`/`operator_edited`/`sent_body` are the edit-rate signal and the only record a first attempt happened, and a resend through `sendDraftById` would overwrite them. Alternates are suggested, never used: guessing an address is what drives the bounce rate that caused this. Three readers treated the failed send as contact made (`lastOutboundAt`, the relationship summary, Tier 1), and `b2b_companies.last_outbound_at` is a **denormalized copy**, so marking the message undelivered was not sufficient on its own — a derived flag has to be chased to every cache of it. Two further traps found only by running it against real data, both of the same family as the mis-parented-thread bugs: **`b2b_messages.to_email` is not reliably one address** (manual sends store the whole To: header, so a row held `"bsullivan@bagly.org, lflynn@bagly.org"` — unsplit it defeated the dedupe and offered back the mailbox just retired), and **a re-run of the catch-up silently did nothing while reporting success**, because `correlateInbound` returned on the duplicate-message insert before reaching the bounce path. A record already existing says nothing about whether its consequences were applied.

- **Scheduling shows the calendar rather than writing times into a draft (2026-08-20):** the obvious build was to have the advisor propose two or three times in the email, which needs availability in its context — and an advisor told to propose times with no slots in context will invent them, in customer-facing text, offering an org a slot that is already booked. Jamie's call was to cut the generated half entirely: the panel is a read-only lookup and he types the times himself. That single decision deleted the trigger rules, the org-only gate, the "slots in context license naming a time" safety property, and a send-time freebusy re-check for drafts that sit pending for days. **Removing the capability was cheaper than making it safe, and at this volume the operator typing two lines is not the expensive part.** What remains automated is the half that was genuinely manual: reading their proposed times, checking three calendars, and turning a chosen slot into an event, an invite and a reply in one action — booking and telling them are deliberately inseparable, because an event the other side was never told about is worse than no feature. Corollaries: their timezone is a deterministic table (a multi-zone country with no region answers NOTHING, since a wrong inference lands verbatim in "…, 1pm your time", and the panel always shows stated / inferred / unknown); Sonnet reads their message but is kept out of offset arithmetic, reporting a wall clock plus the zone they spoke in; busy slots, holidays and hours unsociable for THEM are shown rather than hidden, because for a German or Australian partner every 9-5 Eastern slot is unsociable and an empty grid is worse than an annotated one; and a calendar this token cannot see would contribute no busy blocks and read as free, so the three IDs are asserted at startup rather than assumed. A booked call suppresses the cadence on the same reasoning as On Me — that company is not stalled, it is waiting for a date.

- **A contact change is one operation, not three edits (2026-08-19):** the advisor could read "Riley has left, direct all contact to Matt" out of an auto-reply and say so in the relationship summary while the Send box still addressed Riley, because `resolveRecipient` reads `b2b_contacts` and nothing short of the database could change that row. Knowing a contact has moved on and being unable to act on it is worse than not knowing. `updateContact.js` moves three things together because doing them separately can half-happen: the new person becomes the **only** primary (20 companies already carry several active primaries, which made the actual recipient a function of row order), the named predecessor is deactivated rather than deleted so their history still reads, and `contact_unknown` clears — left set, the cadence refuses to draft for a problem that is now solved. Only the person named in `replaces` is retired: orgs legitimately keep several people on file and only one has left. An address already registered to another company is refused rather than reassigned, because silently moving one is how one org's correspondence lands on another's record. Promote and retire are separate operations from replace, because the person we should be writing to is usually **already on file** — `correlateInbound` auto-registers anyone who writes in from the company's domain — so making the operator retype a name and address the system already holds is busywork, and retyping is where a wrong send address comes from. Retiring deactivates rather than deletes (their address is what makes their own messages resolve to this company) and refuses to remove the last reachable contact when no general inbox exists. Retired contacts stay VISIBLE in the panel under a muted "former" group with a restore: hiding them meant retiring someone erased them from the UI, so you could not see who you had been writing to, could not verify the promise that their history was kept, and could not undo a wrong click. Restore reactivates without making them primary — undoing a removal and choosing a recipient are different decisions.

- **A staleness marker the operator has to notice is not a safeguard (2026-08-19):** the relationship summary carried an "as of / new messages since" marker at the top of its block, which is off screen the moment you scroll down to read a reply — so a recap written before a reply looked identical to one written after it. A correct system therefore read as a broken one: MTPC's summary was generated on 13 August covering 2024, a new contact wrote in to say the old one had left, and the summary appeared to have missed the single most important fact in the thread. The fix is to refresh on open rather than to make the marker louder, skipped only while Gmail discovery is mid-flight (summarising then would recap a record still being imported). General form: when freshness is a correctness property, closing the gap beats labelling it.

- **"We are not working this one" is our decision, not a relationship fact (2026-08-19):** deprioritising a company had no home in the model. `drop` writes `relationship_state='lost'`, which claims they went away or said no — false for a real `in_contact` retailer in a market we chose not to work this year, and it destroys the state we would need to resume. `snooze` demands an end date that an indefinite decision does not have. So pausing is an orthogonal pair (`outreach_paused_at` / `_reason`), never a `relationship_state` value: the company keeps being exactly what it is, and only our intent toward it changes. Snooze and pause are now the same mechanism with different endings (dated vs indefinite), unified behind `deferredSince`. **The rule that constrains both: deferring clears a reply that was already sitting there, and can never suppress one that arrives afterwards.** Tier 1 previously outranked everything, which made both controls useless for the companies that most needed them (all three of the first real cases were Tier 1). Letting a deferral silence a *live* correspondent would deliberately rebuild the failure that left four partners waiting, one for 332 days — so the comparison is against the moment the deferral was set, which is why `snoozed_at` had to be recorded separately from `snoozed_until`. A pause with no recorded set-time suppresses nothing rather than guessing. **The panel does not render the cadence's output**, it renders `mergePendingDraftEntries`, which re-adds any company holding a pending draft *without consulting the cadence*, at the tier and reason frozen on the draft row — so the first version cleared all three companies from `fetchOutreachQueue` and left them visibly unchanged on screen, at a stale "now due". Deferring therefore supersedes pending drafts (a pending draft IS a chase waiting to be sent), and the merge independently excludes deferred companies. Verify a queue change against `fetchQueueWithDrafts`, never `fetchOutreachQueue`.

- **A deferral where the work is still live is a different thing from one where it is not (2026-08-20):** pause and snooze both mean "we are not working this relationship", so both supersede the pending draft. "On me" — Jamie owes them an answer but not today — is the opposite: the work stays his, so it KEEPS the draft, which is what he wants in front of him when he picks it back up rather than a second Opus call to recreate what he already read. That inversion is what makes the merge exclusion load-bearing rather than a backstop: `mergePendingDraftEntries` re-adds any company holding a pending draft *without consulting the cadence*, so a disposition that keeps its draft and does not exclude itself there puts the company straight back in the queue it was claimed out of, and the button appears to do nothing. All three are held to the rule that governs the family (a deferral clears a reply already sitting there and can never suppress one that arrives afterwards), and On Me is where breaking it would be easiest to excuse — "I know, it's on my list" is the exact sentiment that left four partners waiting, one for 332 days. The list carries days-on-you, a count on its own tab, and a digest section, because a queue-relief valve with no ageing is just a quieter backlog. What each claim is *about* is answered by the relationship summary's suggested next step rather than by a note typed at claim time: the next step is derived from the conversation and rebuilt as messages land, where a note is written once and then decays on the one list whose defining problem is age — and asking for it put a prompt in front of a decision whose value is that it takes one click. Fixed alongside: `resume` nulled only the pause columns, so the "Resume now" beside a live snooze reported success and changed nothing.

- **A claim is discharged by doing the thing, not by them writing back (2026-08-26):** On Me originally ENDED when a newer inbound landed, derived by comparing it against the claim stamp, on the reasoning that a row cannot be on both the queue and the On Me list without one of them lying about who holds it. That conflated two questions the surfaces answer separately: the queue asks what is DUE, On Me records what Jamie has personally taken on. An org replied "Awesome, thanks so much!" three minutes after being claimed and retired a claim whose actual subject was the tabling cards he had just promised them — an acknowledgement erasing the only record of an obligation it did not touch, on the one list whose defining problem is age. A claim now clears on **send or Back to queue and nothing else**, a company can sit on both surfaces, and the On Me row is badged "they replied since" (styled as the queue's own Tier-1 badge, because it is the same fact) since what you owe them may have just changed. The safety property was never enforced here and is untouched: it lives in `deferredSince`/`staleReply` inside `computeQueueEntry`, so a live correspondent surfaces at Tier 1 whether or not the claim survives — worth checking which line actually carries a guarantee before treating a rule about deferrals as load-bearing for it. What made the defect visible was the panel banner reading `on_me_at` raw while the list applied the derived test, so the two surfaces the derivation existed to keep in agreement were exactly the ones that disagreed: **a rule derived in one place and re-read raw in another is not derived, it is duplicated.**

- **An absent record and an empty one are different answers, and the engine must not conflate them (2026-08-19):** thread discovery ran only when an operator opened a company, so 197 of 242 companies held zero messages — and the cadence read `lastOutboundAt IS NULL` as "never contacted". That is not a gap, it is a confident wrong answer: an org that wrote to us last month sat at Tier 3 "no prior outbound" instead of Tier 1 "waiting on us", and the advisor drafted a cold opener off it. The fix is to go and look (a nightly sweep) rather than to teach the rule about nulls, because the rule cannot distinguish the two cases from the data it has. Generalises to any queue built on the absence of a record: before a branch treats "no rows" as a fact about the world, something must have actually checked. Corollary on backing off: the sweep withholds its searched-stamp when writes fail, because a run that wrote nothing would otherwise record itself as "looked, found nothing" and go unretried — the same self-certifying silent failure as a leaked claim.

- **ON CONFLICT cannot infer a PARTIAL unique index (2026-08-19):** the `UNIQUE(company_id, gmail_thread_id)` index is partial (`WHERE gmail_thread_id IS NOT NULL`, since a thread sits uncorrelated until its first send or receive), and an upsert naming those columns fails on every row with "no unique or exclusion constraint matching the ON CONFLICT specification". It shipped green because the only caller logged and continued, and it only ran from the panel. Where a natural key is partial, use insert-then-refetch-on-conflict rather than upsert. The wider lesson is about the failure mode, not the SQL: a write path that logs and continues will pass tests, pass review, and deploy silently broken — the calls-per-output tripwire applies to writes too.

- **A shared Gmail thread is two relationships, so it gets two rows (2026-08-13):** `b2b_threads.gmail_thread_id` was UNIQUE, which makes the common case unrepresentable — Gmail threads on subject, so one conversation regularly holds two orgs (13 of ours). Every writer then keyed on `gmail_thread_id` alone, and the damage compounded down the chain: `correlateInbound` and `discoverCompanyThreads` filed a company's messages onto whichever org's row existed first (105 messages, 8.9% of the corpus), and the discovery upsert's `onConflict: 'gmail_thread_id'` went further and **rewrote the existing row's `company_id`**, handing one org's entire conversation to another. The panel reads a conversation by thread ownership, so it simultaneously hid messages that were genuinely a company's and showed another org's under their name. Now `UNIQUE(company_id, gmail_thread_id)`, every thread lookup is company-scoped, and status is per-row so Close/Reopen means something per relationship. The generalisable point: a uniqueness constraint is a claim about the world, and `UNIQUE(external_id)` on anything sourced from a shared external system asserts that the external entity belongs to exactly one of ours. When that is false the constraint does not merely fail to help — it forces every writer into a silent overwrite. Third instance of this family after the per-message thread-membership fix (import side) and the domain-matching rule; the shared thread was the READ and CONSTRAINT side of the same problem. One deliberate asymmetry: the bounce branch of `correlateInbound` stays unscoped because it is trying to *discover* the company, but it now refuses to guess when a thread has several owners — marking the wrong org's contact as lost pauses their cadence.

- **A summariser's freshness test must be a data boundary, not a wall clock (2026-08-13):** the pre-migration summary feature was never removed — `threadBuilder.js` still runs it daily — but it writes `email_threads` keyed on `gmail_thread_id` while the engine reads `b2b_messages`, and only 11 of 242 companies were reachable across that gap. Rebuilding it company-level exposed the deeper flaw in the original: it selected new messages with `date > summary_updated_at`, a *generation time*. History in this system arrives BACKWARDS (`discoverCompanyThreads` imports old threads long after a company has been summarised), so anything landing below that timestamp is invisible forever. The watermark is therefore the `sent_at` of the newest message included, paired with a message count — the count is the only thing that can see an insert behind the watermark, and a message at or before it means the narrative it belongs inside is already written, so it forces a full rebuild rather than an append. Any incremental summariser over a corpus that can gain history retroactively has this bug. Two supporting calls: the suggested next step is **advisory** and never writes `next_action_date`, because `cadence.js` already owns what is due and two authorities would disagree; and the sheet-era `ai_summary` is retained untouched as dated prologue rather than overwritten, because for companies whose history was never imported it is the only relationship knowledge we hold.

- **A summary written in relative time is a stale fact with a long fuse (2026-08-13):** `threadBuilder` injects today's date into its prompt and still produced 52 of 54 summaries phrased "about 10 months ago" / "scheduled a call for today" — anchored to a generation date the reader never sees, and fed to the advisor verbatim years later. Injecting the date fixes the model's *reading* of the transcript; it does nothing about its *writing*. The output rule has to be stated positively with a verbatim template ("Write every date absolutely: 'in March 2026'"), per the positive-rules-stick pattern. Same exposure as the "632 items distributed this year" incident, one layer further back.

- **Identity across the B2B stores is matched on domain, never on name (2026-08-11):** the same org exists in `donation_partners`, `b2b_companies` and Gmail, and every name-based join we have written has eventually fused two unrelated orgs. A name fallback put "Trans Healthkit Projekt" (Hagen) and "Transhealth" (Northampton MA) on one record, so a German partner's context carried an American clinic's 2022 thread. Domain-only matching, and **no match must mean no facts rather than a guess** — a wrong join here does not fail loudly, it silently puts one org's shipment counts and history into another org's email. Same class as the per-message thread rule below. `syncB2bCompanyState` still carries a name fallback and is the remaining instance (parked). Corollary: an org missing from `b2b_companies` entirely is invisible to the engine, not merely incomplete, so partner-registry backfill is a correctness concern and not housekeeping.

- **The advisor is given facts it would otherwise have to ask for (2026-08-11):** where our own records can answer a question we are about to put to a partner, the record goes in the context and the question gets sharper. Donation shipment counts and dates turn "are you receiving our packages?", which the org has to go research, into something answerable in one line. Two constraints make it safe: the context states these are our SEND records and never confirmation of receipt, and a zero or low count is surfaced explicitly so the advisor acknowledges it instead of implying a flow of donations that is not happening. Same reasoning applies to the partner discount rate, which is a country lookup the advisor should never be left to derive.

- **One row per org per relationship_type, and the recipient must never depend on row order (2026-08-11):** duplicate rows are not a cosmetic data issue, they silently break the panel's read of a relationship. The bare BAGLY row showed "no prior outbound, this will be the first touch" for a partner with 35 messages and 13 packages routed on its sibling, and `hasEngagedSibling` does not help because it only suppresses a cold OPENER, not a checkin drafted off an empty record. Merged on domain, within relationship_type (a retailer and an org can share a domain legitimately). The related trap: `resolveRecipient` ordered by `is_primary` and took `limit(1)` with no tiebreaker, and 20 companies carry more than one active primary, so who actually received an email was down to whatever order Postgres returned. Any "pick one row" query on data this messy needs a total ordering, and where the correct pick is a human decision rather than derivable (a named successor contact beats the address they replaced), it has to be stated in the data. **`website` is not reliably a website:** some rows were populated from the contact's email domain, so it held `gmx.net` (a free mail provider) and `bit.ly` (a shortener). Those defeat domain matching, and worse, a future merge keyed on domain would fuse every unrelated org sharing one. So domain matching needs a junk-domain denylist, not just the free-mail one, and a merge sweep must also cover rows with a NULL or junk website, which a domain-keyed pass cannot see at all: three duplicates survived the first merge that way, including one this session created by adding a partner row for an org that already had one under a different name.

- **Inbound correlates on sender DOMAIN, not just the exact address, and what fails to correlate must be visible (2026-08-11):** `correlateInbound` matched `b2b_contacts.email` / `general_email` exactly, so a colleague of the person we had on file was dropped with `return { matched: false }` and no trace. That is not rare: 16 of 45 uncorrelated threads were companies we already knew. The damage is not a missing message, it is an actively false queue — four orgs (Unity Conejo, SoCirC, Lumenus, Fenway) had **replied and been waiting 65-120 days** while the panel showed them as "no prior outbound", i.e. as cold prospects to introduce ourselves to. Now a sender whose *identifying* domain matches a company's website or an existing contact attaches, and the address is auto-registered non-primary so the exact match wins next time. Safe only because generic domains are excluded — see `emailDomains.js`, which is the single denylist for free mail, shorteners and page builders, and should be used by anything matching on domain. The general rule: a correlation step that can fail needs somewhere for its failures to land, because silent `matched: false` is indistinguishable from "nobody wrote to us."

- **Thread membership is decided per MESSAGE, not per thread (2026-08-07):** Gmail threads on subject, so two unrelated conversations sharing one get filed together — "agreement and next steps" went to both Trans Closet of the Hudson Valley and Transformation Closet (Nova Scotia), and importing the thread wholesale put one org's messages on the other's record. 120 of 545 messages (22%) were mis-attributed across 7 companies before this was caught; The Tool Shed held 61 messages of Early To Bed's conversation, and the advisor drafted from it. A message is now imported only when one of the company's known addresses appears in its from/to/cc. Our own address never counts as evidence of membership — every message has jamie@ on one side, so counting it keeps everything. Companies with no addresses on file are skipped rather than emptied: missing contact data is not evidence a message is foreign.

- **The partnership agreement is generated, not written (2026-08-06):** `donationAgreement.js` renders the LGBTQ+ Organization Donation Program agreement as a pre-signed PDF from a fixed HTML template — deliberately no AI anywhere in it. It is a contract, so the clause wording must be byte-identical every time or we cannot say what we agreed with a given partner; the only variables are the org name and the discount, and the discount is a country lookup (US/Australia 50%, elsewhere 30%, matching wholesale — the gap covers duties we absorb). Jamie's signature is embedded and the counter-signature line left blank, matching the pre-signed copies partners already receive. The email AROUND it stays advisor-written, because that genuinely varies (a re-approach after a year of silence reads nothing like a post-call follow-up). The country lookup has NO exceptions (2026-08-11): a German partner held a signed agreement stating 50%, issued in error before the rule settled, and the call was to move them to the standard 30% rather than carry a permanent carve-out for one mis-issued document. If a partner raises it we say plainly that we made a mistake. One rate table, no per-partner overrides to remember or leak into a draft.

- **Never guess an email address; use the contact form (2026-08-06):** small orgs often publish only a form. Inventing `info@` to make them sendable trades a real risk for a fake convenience — unverified addresses drive bounce rate toward the ~2% that burns sender reputation, and that damage lands on rubyshines.com, the same domain Klaviyo uses to reach customers. A form is also usually the channel a small org actually monitors. So `contact_form_url` is a first-class delivery channel: the draft is written normally, `sendB2bEmail` fails closed, and the panel hands over copy-paste text plus the link. The channel is **derived, never stored** (`deliveryMode`: an email on file always wins), so adding a contact later upgrades the company silently with no flag to un-set. Delivery never affects tier — priority stays signal-based; it only breaks ties within a tier so manual sends batch together.

- **One send path, whoever wrote the email (2026-08-06):** the panel's empty state is its front door, not an edge case — drafts are generated on demand, so every company starts with no draft and returns to none after each send. Typing a reply you already know the words to should not require a ~$0.07 Opus call first. So the operator can compose directly, but the text is stored as a `b2b_drafts` row and sent through the *same* path as an AI draft, rather than getting a second send path that would drift on thread bookkeeping and cadence dates. `advisor: null` on that row is the training signal that matters: it separates "Jamie wrote this himself" from "Jamie edited the AI's draft", which the `operator_edited` boolean alone cannot. **The composer autosaves into that row as you type (2026-08-19)**, because the text used to exist only in a textarea until Send: a refresh, a closed tab or a failed send destroyed it with nothing to recover, and the row shape for it already existed. Autosave deliberately refuses to touch an ADVISOR draft — there, `subject`/`body` are the AI's originals and their pair with `sent_subject`/`sent_body` IS the edit record, so writing over them would destroy the very signal this decision exists to capture. In-progress edits to an AI draft therefore remain send-time only.

- **`relationship_state` is not a funnel stage (2026-07-29, data fixed 2026-08-05):** `in_contact` was doing double duty — an import nobody had emailed and a retailer mid-samples-conversation held the same value, so no cadence rule could tell them apart. `prospect` now carries "never approached" (143 rows reclassified); a company leaves it on any evidence of a relationship (outbound, a thread, samples, an order, or prior-history `ai_summary`). Anything presenting a pipeline stage must still derive it, and must keep *relationship* (account / lead / lost) separate from *conversation* (talking / closed / never): folding them into one filter hid active retailers whose threads had all concluded, which is exactly the set worth working. `dormant` is still written by nothing, so `reactivation` remains unreachable (parked).

- **Tier-4 first-touch is admission-gated, not automatic (2026-08-05):** the tier existed in `TIER_BY_TYPE` from the start but no cadence branch ever returned a first-touch type, so the whole discovery backlog was invisible and the panel read as empty. Turning it on makes ~200 imported rows eligible at once, and they are not equally ready — donation-form orgs answered a survey, CenterLink rows are a name slug and an email. So Tier 4 requires `vetted_at`, set per company by `b2b_triage` (keep / drop / snooze, no draft generated). Supply is let in cohort by cohort. If a future session finds Tier 4 quiet, the answer is to admit a cohort, never to remove the gate.

- **A cold opener is suppressed when a duplicate row for the same org is already engaged (2026-08-05):** the imports created two rows per org in several cases (BAGLY exists as an active donation partner and as a bare row with a different address). Introducing ourselves to an existing partner at their `info@` is the worst email we can send. The guard is domain-based and queried per company rather than derived from the queue's company list — `generateDraftForCompany` builds context for a single company, so a list-derived guard would be bypassed by the draft button. It suppresses the opener only; ongoing cadence for the engaged row is untouched.

- **`$0` Shopify orders tagged `sample*` are a samples event, not revenue (2026-08-05):** sample kits ship as $0 orders (`sample kit reach out`, `wholesale-samples`). Counting them as purchases promoted 15 retailers to `active` as if they were customers, while `samples_shipped_at` stayed null so the samples cadence never fired for anyone. Purchases are price-driven; sample orders populate `samples_shipped_at`, bounded to 60 days so a backfilled historical sample can't trigger a checkin months late. Applies to any future B2B revenue analysis, not just cadence.

- **Deleting a feature's code does not delete it from the advisor's prompt (2026-08-13):** `affiliate_invite` and `affiliate_reactivation` were removed from the cadence in August as unreachable, and the affiliate onboarding flow was never built — no app, no payout, zero affiliates on the books. Both advisor prompts went on describing the program as live and quoting "roughly $7-10 per order", and the sales prompt told every cold retailer intro to use two-door framing. So the engine has been offering retailers a program that does not exist, and a Tier-1 reply drafted for a store that had asked about it stated flatly that it was "up and running now". The prompts now say plainly that it does not exist and must never be offered. **When a capability is cut, grep the prompts for it in the same change** — the prompt is a product surface, not documentation, and an advisor cannot know that code was deleted underneath it. The advisor's own `facts_to_verify` caught the discrepancy; the body still asserted it, so that field is a review aid and not a guard.

- **Cadence branches may only read context `buildContexts` actually sets (2026-08-05):** seven branches were unreachable for months because they gated on ctx fields the context assembly never assembled — the table was written to the design, the context to what Tier 1 needed, and nothing failed loudly in between. `purchase_pitch`, `affiliate_invite` and `affiliate_reactivation` were deleted rather than left looking live; a test asserts they stay gone so reinstating one without its data fails loudly.

- **Within a tier, order must encode readiness, because operators read order as priority (2026-08-11):** the queue's comparator sorted on tier and then returned 0, so within a tier the order was whatever Supabase happened to return, and synthetic pending-draft rows were appended last. Eighteen reviewed, ready-to-send drafts therefore sat BELOW eight companies with no draft and no imported history, and it read as though the empty rows were the more urgent work. Ready work now sorts first within a tier, still under Tier 1's oldest-waiting-person rule. The general lesson for any operator surface: a list with no meaningful secondary sort is not neutral, it actively communicates a priority that does not exist, so either sort it deliberately or say in the UI that the order is arbitrary.

- **The queue stays due-only; browsing is a separate surface (2026-07-29):** the 6-tier queue answers "what needs action" and nothing else. Reaching a company the cadence hasn't surfaced is the directory's job, and drafting from there is explicitly operator-initiated (`force`), never a relaxation of the cadence rules. The advisor is told which of the three it is — a typed cadence message, an operator revival, or a genuine Tier-1 reply — because its default framing ("they are waiting on a reply from us") is false for the first two and shows up in the copy.

- **Only the per-company view guarantees a complete conversation (2026-07-29):** `reconcileThreads` skips closed threads by default (a concluded thread can't change what's due, and the queue-wide sweep would otherwise cost a Gmail call per thread); the panel's one-company sync passes `includeClosed`. Discovery repairs threads it already knows rather than skipping them, and never re-derives status on an existing thread — the operator may have just closed or reopened it by hand.

- **Reorder cadence is frequency-aligned, not flat (2026-07-24):** nudge threshold = 0.75 × the company's LATEST order interval, clamped 90-365d, computed by the daily sync (last interval beats median/mean because bursty histories lie in both directions — Transting: monthly cluster then a 402d gap). The advisor can override timing per-send via `next_touch_days` when the thread gives a concrete reason (stated timeline, rough-patch-then-comeback), bounded 7-365d. Math sets the default; thread judgment bends it; the operator sees the override before sending.

- **Never manually parse CSV data** — always pass raw CSV to `parse_wholesale_input` tool.
- **Order creation tool selection:** `create_wholesale_order` requires an existing Shopify customer ID — use it for established wholesale accounts. For one-off bulk or community orders where the customer may not be in the system yet, use `create_order` with `discount_percent: 50` — it finds or creates the customer automatically from email + name + address.
- **Two-tier discovery:** Google Maps for breadth, then deep research for depth.
- **Domain dedup:** Merge sources if domain already exists, don't duplicate.
- **Shipping speed driven by Shopify shipping method title.** All order-creation tools (`create_order`, `create_exchange_order`, `create_invoice_order`, `create_wholesale_order`) take `shipping_speed: 'standard' | 'expedited'`. The Shopify shipping line title is set via `getShippingMethodTitle(country, speed)` (in `orderUtils.js`) at price `$0.00` — Warehance auto-maps the title to the correct carrier (US Standard / US Expedited / Passport DDP / Passport DDU / Fedex). No FedEx tags. Wholesale defaults: standard for US, expedited for non-US (preserves the prior "non-US wholesale = FedEx" rule). Post-creation `update_shipping_speed` is fully programmatic: US standard ↔ US Expedited; non-US standard maps zone → Passport DDP (Canada / DDP) or Passport DDU (DDU / unknown); non-US expedited → Fedex. Incoterms is implicit in the Passport method name and handled automatically by Warehance for Fedex orders. Shipping is free by default but can carry a real charge via `shipping_price` (2026-08-12). It may only ride an **expedited** title: every standard rate is literally named "Free … Shipping" because that string is what Warehance matches on to pick a carrier, so a charge on one would invoice a contradiction we cannot fix by renaming. Charging via a custom line item instead is a trap — `discount_percent` applies per line item, so it silently halves. **Partner incoterms override the zone default by picking the other title (2026-09-02):** the title is the entire DDP/DDU signal — Warehance automation rules match it to set carrier + incoterms (e.g. "Expedited International Shipping" → FedEx + DDU) — so a DDU partner in a DDP-zone country just gets the plain international title, and the wholesale preview reads the Terms line off the title actually set rather than re-deriving it.

- **Shopify draft-order discount amounts are in the order's BASE currency, never the presentment currency.** `credit_items` on `create_wholesale_order` comps defect units by summing their wholesale unit prices into one order-level fixed-amount discount, and that sum has to be computed in USD — passing a presentment-currency figure on an AUD order over-credits by the whole FX factor, silently and in the customer's favour. Applies to any fixed-amount discount we apply anywhere, not just this tool. **The AU de minimis split is decided in AUD whatever the invoice currency (2026-09-03):** customs values the parcel in AUD, so a forced-currency partner (Sock Drawer Heroes, Tuck and Bind) is probed in AUD at Shopify's live rate, then re-created in USD one draft per split. Because customs converts a non-AUD invoice at the export-day rate rather than the probe's, those orders split against a threshold with an FX margin instead of the full $1,000.
- **`pre_increase_pricing` flag on `create_wholesale_order`:** When set, per-line prices use `price_history.previous_price` from the Apr 16 2026 rollout row × country discount, instead of current retail. SKUs without an Apr 16 row fall back to current retail silently. No draft-level `appliedDiscount` when flag is on — discount is baked into per-line prices. When all partners have transitioned to current pricing, remove the flag (park a cleanup entry at that time).
